# ALinkSec 双数据库与轻量化部署改造计划

## 1. 目标

在不降低现有 PostgreSQL 生产部署可靠性的前提下，增加 SQLite 轻量部署：

- `postgres`：PostgreSQL 17 + VictoriaMetrics，面向正式环境。
- `sqlite`：SQLite WAL，默认关闭 VictoriaMetrics，面向开发、演示及少量主机。
- 两种模式复用同一套业务接口、权限模型和 Agent 协议。
- SQLite 用于日常功能验证；PostgreSQL 集成测试仍是生产兼容性的最终依据。

## 2. 支持边界

| 项目 | PostgreSQL 模式 | SQLite 模式 |
|---|---|---|
| 建议规模 | 正式环境 | 初始承诺 1～10 台受管主机 |
| 服务实例 | 可演进多实例 | 单实例 |
| 数据文件 | PostgreSQL 数据卷 | 本机持久化卷中的单个数据库文件 |
| 时序指标 | VictoriaMetrics | 默认关闭，可独立启用 VictoriaMetrics |
| 高可用 | 依赖外部数据库能力 | 不支持 |
| 网络文件系统 | 由 PostgreSQL 管理 | 禁止将数据库放置在 NFS/SMB |

SQLite 模式启用 WAL、外键约束和锁等待；数据库文件必须受操作系统权限保护。运行中备份使用 SQLite backup API 或 `VACUUM INTO`，不得只复制主数据库文件。

## 3. 技术方案

### 3.1 配置与启动

- 默认 Profile 为 `postgres`，保持现有部署行为。
- 增加 `application-postgres.yml` 与 `application-sqlite.yml`。
- 增加 `docker-compose.lite.yml`，仅启动 server 与 web，SQLite 文件落在 `server-data`。
- 轻量模式默认设置 `ALINKSEC_METRICS_ENABLED=false`。

### 3.2 Schema 与迁移

- PostgreSQL 继续使用外部、最小权限的版本化迁移流程。
- SQLite 在 DataSource 对业务 Bean 可见前执行版本化迁移。
- SQLite 迁移记录版本、说明和 SHA-256；已执行脚本发生变化时拒绝启动。
- SQLite 初始 schema 由 PostgreSQL 空库 schema 机械生成，生成规则和产物都纳入版本控制，CI 校验二者一致。

### 3.3 SQL 兼容策略

- 优先使用双方兼容的 SQL：`CURRENT_TIMESTAMP`、`CAST(... AS TEXT)`、`LOWER(...) LIKE LOWER(?)`、`CASE` 聚合。
- 集合条件改为参数化 `IN`，不再依赖 PostgreSQL 数组参数。
- 时间区间在 Java 侧计算并绑定，避免 PostgreSQL `interval` 方言。
- JSON 仅在少量提取场景由数据库方言提供表达式，其余作为合法 JSON 文本存储。
- 趋势日期分桶等无法通用的查询只封装必要片段，不复制整套 Repository。

### 3.4 验证

- SQLite 使用临时真实数据库执行建库、迁移和核心业务冒烟测试。
- PostgreSQL CI 保留 schema、迁移重复执行和最小权限验证。
- 两种数据库执行同一组数据访问契约测试。
- 继续执行 Maven、Go、前端测试与生产构建。

## 5. 完成标准

1. `SPRING_PROFILES_ACTIVE=sqlite` 可在没有 PostgreSQL 的环境启动服务。
2. SQLite 首次启动自动建库，重复启动不重复迁移，脚本篡改会阻止启动。
3. 登录、注册、主机/资产、任务、告警、指令 ACK、审计等核心链路通过 SQLite 真库测试。
4. 生产 Compose 和 PostgreSQL schema/migration 检查保持通过。
5. 文档明确模式选择、容量边界、备份恢复和从 SQLite 切换到 PostgreSQL 的限制。
