## 已知事实与历史限制

候选 `6f32aae` 的 CI 45037371770 首轮 Windows 2022 在恢复断言失败：最后一次 CPU=0、倍率 2、原因为 `cpu_pressure`；同源仅失败作业重试通过。此前 Windows 2025 也出现同类末状态。[93 号记录](93-复查运行维护与大屏补证.md)及 PR 保留原失败，不能据重试通过宣称根因已修复。

原测试等待最多 14 次，未独立确认其中是否包含连续 10 秒低负载；它只在成功时写出采样，上传步骤也缺少 `always()`。因此旧失败缺少逐样本累计时间，无法确定具体是否有 CPU 峰值、计数中断或其他因素。

确定性反例先施加持续负载进入 2 倍退避，再在空闲第 5 秒加入一次 4% CPU 样本。第 14 秒末 CPU 已为零，但距该峰值只有 9 秒有效低负载，正确状态仍为 2；下一秒满窗才恢复。该反例说明旧断言的前提不足，**不证明历史 Windows 运行实际出现了这条采样序列**。

已完整下载并校验 `16f8287` 两版 Windows 的资源 ZIP：各含 21 份旧格式状态，正常记录均在连续低负载满 10 秒后恢复。它们只说明该次成功，不补造旧失败的观测。

## 改动和判定

- 生产 `Governor`、原生计数读取和资源配置保持原样；变更限于测试、CI 留存和说明。
- 原生检查从原始累计 CPU、RSS 及采样时间重算当前低负载后缀，不依赖被测限流器给出的 CPU 百分比来决定窗口是否完整。提前恢复或满窗未恢复均失败。
- 恢复期间插入一次真实 CPU 工作负载，确认它打断窗口；每次测试最多观察 30 秒恢复场景，整个测试仍受 1 分钟超时约束。CPU／恢复窗口仍为 10 秒，既有 RSS 触发、回收、软内存目标、共享 I/O、取消与采样失败断言保留。
- 普通错误和断言失败通过测试清理回调写出部分证据；不在采样期间写盘，以免证据 I/O 改变被测 CPU。受控子进程故意触发计数读取失败，验证失败标志、阶段、原始错误和采样状态确实写出。
- CI 对 Windows 2022／2025 各验证三个独立测试进程，任一失败立即停止；各进程独立文件，已有证据始终尝试上传。Linux amd64／arm64 各保留一次原生检查及失败证据。27 项必需作业集合和原门禁不变。

## 原始证据与验收边界

`resource-validation-*` ZIP 保留 `checks`／`samples`，另含 `observations`、配置、当前阶段、失败原因、起止时间、进程 ID、源码／run／attempt。每次观测包含累计 CPU、RSS、时间、单调采样间隔、状态及读取错误，可从原始输入复算负载与窗口。Windows 使用 `run-1.json` 至 `run-3.json`，Linux 使用 `result.json`；不能把一次失败后的新进程误当作原进程恢复。

本机在内存／PSI 看门狗下串行执行确定性用例、Linux 原生场景及相关 race 检查；受控错误回归是夹具验证，不冒充 Windows 真实失败复现。跨平台结果、完整 CI、产物来源／完整摘要和合并主线接受按 PR 中各自精确 SHA／run 记录。历史首轮失败没有原始采样，具体原因继续保持未确认；本批修正恢复判定前提并保证后续普通失败可观测，不替代现场长稳性能验收。
