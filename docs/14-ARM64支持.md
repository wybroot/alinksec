# Linux ARM64 支持

当前开发分支新增 Linux ARM64（aarch64）支持。已发布的 v0.0.1 镜像与附件仍只有 amd64；ARM64 改动需通过原生 ARM CI 后随新版本发布。不要在 ARM 主机上直接使用 v0.0.1 的 amd64 Agent。

## 平台范围

| 组件 | 当前源码与发布流程的目标平台 |
| --- | --- |
| Server、Web、SQLite 维护工具 | Linux amd64、Linux arm64 |
| 原生 Agent | Linux amd64、Linux arm64、Windows amd64 |

ARM64 使用 64 位 Linux 和 systemd，`uname -m` 通常返回 `aarch64`。本次不包含 ARMv7/32 位 ARM、Windows ARM64 或 macOS Agent。管理端和 Agent 的 CPU 架构可以不同，通过同一套 TLS/gRPC 协议通信。

## 从源码构建 Agent

在当前源码根目录运行，要求 Go 1.24+；可以在 amd64 构建机交叉编译：

```bash
mkdir -p release-bin
cd agent
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags '-s -w' \
  -o ../release-bin/alinksec-agent-linux-arm64 ./cmd/agent
```

交叉编译成品需在 ARM64 主机运行。将二进制、管理端导出的 CA 证书及 `deploy/agent/alinksec-agent.service` 传到目标主机，然后安装：

```bash
sudo install -m 0755 alinksec-agent-linux-arm64 /usr/local/bin/alinksec-agent
/usr/local/bin/alinksec-agent version
sudo /usr/local/bin/alinksec-agent install \
  --server <server-address>:9443 --token <ENROLL-token> --ca-file ./alinksec-ca.crt
sudo install -m 0644 alinksec-agent.service /etc/systemd/system/alinksec-agent.service
sudo systemctl daemon-reload
sudo systemctl enable --now alinksec-agent
```

防护所需的 Linux 权限、iptables、SSH 日志来源与 CA 配置参见 [部署文档](06-部署文档.md)及 [登录与文件防护](11-登录与文件防护.md)。

## 从源码构建管理端

在 ARM64 Linux 构建机上，从当前源码根目录依次构建三个组件；Docker 默认使用本机架构：

```bash
docker build -f deploy/docker/Dockerfile.server -t alinksec-server-dev:arm64 .
docker build -f deploy/docker/Dockerfile.web -t alinksec-web-dev:arm64 .
docker build -f deploy/docker/Dockerfile.sqlite-maintenance -t alinksec-sqlite-maintenance-dev:arm64 .
```

在部署使用的 `.env` 或 `.env.lite` 中指定开发镜像：

```dotenv
ALINKSEC_SERVER_IMAGE=alinksec-server-dev:arm64
ALINKSEC_WEB_IMAGE=alinksec-web-dev:arm64
ALINKSEC_SQLITE_MAINTENANCE_IMAGE=alinksec-sqlite-maintenance-dev:arm64
```

然后按 [部署文档](06-部署文档.md)配置凭据、端口、证书与持久化卷，使用 `--no-build` 启动所需服务。新版本发布后，同一组件版本标签会同时包含 amd64 和 arm64，由 Docker 自动选择本机架构；也可以固定 `release-manifest.json` 中的索引 digest 或对应平台 digest。

构建机内存应能容纳 Maven/Node 构建。约 2 GiB 主机遵守 `AGENTS.md`：构建与验证串行、运行前检查 RAM/swap、使用资源限制和内存 watchdog，前端构建前暂停后端；本地资源不足时使用同一提交 CI 的 `web-dist-arm64` 产物或在资源充足的 ARM 构建机生成镜像。不要在低内存机器启动整套验证栈。

## 验证与发布

- `CI` 的 `build-and-test (amd64)` 和 `build-and-test (arm64)` 在对应架构的原生 runner 上分别执行 Go 测试/防护 race 检查、实际 Agent mTLS/采集/防护联动、Java 测试、SQLite 维护、容器启动及 PostgreSQL/SQLite API 检查。ARM CI 使用 `ubuntu-24.04-arm`。
- 版本检查、发布门禁和二进制/镜像清单检查可单独运行：`node --test --test-concurrency=1 deploy/tests/release-*.test.mjs`。
- Release 在两种原生架构上串行构建、冒烟，再将已验证镜像的不可变 digest 合并为多架构标签。发布门禁拒绝缺失 ARM 作业的旧 CI 结果，三个 Agent 附件必须来自同一次完整 CI。
- 升级包的平台选 `linux-arm64`。混合架构批次中只要有一个目标不匹配，平台会在下发前拒绝整个批次；Agent 也会在替换文件前核对 Go 构建信息中的 OS/架构，避免误标包损坏安装。

本机交叉编译通过仅说明代码可生成 ARM64 可执行文件，原生运行结果以该提交的 ARM CI 为准。已有 v0.0.1 的性能采样不能作为 ARM 性能结论。

原生 runner 与多架构镜像机制参考 [GitHub runner 文档](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)及 [Docker 多平台构建文档](https://docs.docker.com/build/ci/github-actions/multi-platform/)。
