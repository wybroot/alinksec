## 候选固定与执行顺序

1. 核对本地分支、提交范围与工作区，将最终 HEAD 记为候选 SHA；保留基线 main `b40dc90895ff6dde30e730af7000b7b773e18234` 和修复链。恢复远端阶段时先核对远端 main；若已变化，在同一修复批次内处理集成并重新固定候选，不把 PR 堆叠到另一条未合并分支。
2. 在具备有效 GitHub 认证并恢复统一远端阶段后推送候选，启动完整 CI。当前 [ci.yml](../.github/workflows/ci.yml) 对 push 忽略 Markdown；文档提交可能没有 push CI，须显式 workflow_dispatch。所有 `*_only` 输入保持 false，不能用单平台或局部工作流替代完整验收。

4. 实现、完整 CI 和 review 完成后才创建 PR；已有 PR 在继续改进期间保持 draft。按既定授权合并后核对合并源，启动精确 merged-main 的完整 CI，检查通过后同步规范本地 main。
