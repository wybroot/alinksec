## 候选固定与执行顺序

1. 核对本地分支、提交范围与工作区，将最终 HEAD 记为候选 SHA；保留基线 main `b40dc90895ff6dde30e730af7000b7b773e18234` 和修复链。恢复远端阶段时先核对远端 main；若已变化，在同一修复批次内处理集成并重新固定候选，不把 PR 堆叠到另一条未合并分支。
2. 在具备有效 GitHub 认证并恢复统一远端阶段后推送候选，启动完整 CI。当前 [ci.yml](../.github/workflows/ci.yml) 对 push 忽略 Markdown；文档提交可能没有 push CI，须显式 workflow_dispatch。所有 `*_only` 输入保持 false，不能用单平台或局部工作流替代完整验收。
3. 核对 run 的 head SHA、分支、事件与全部必需作业；下载该次运行产物，核对源码、Agent、镜像和前端证据的对应关系。出现修复提交则候选失效，重新跑最终候选所需完整检查。
4. 实现、完整 CI 和 review 完成后才创建 PR；已有 PR 在继续改进期间保持 draft。按既定授权合并后核对合并源，启动精确 merged-main 的完整 CI，检查通过后同步规范本地 main。
5. 软件验收仅覆盖实际候选和执行范围。现场 25／26／27 保持延期，第 28 项全新部署 N/A；版本发布、生产部署和对外发送通知另按用户指示执行。

以下命令仅为后续执行模板，本地准备阶段没有运行：

```bash
candidate_sha=$(git rev-parse HEAD)
gh workflow run ci.yml --ref fix/review-defects
```

## 必需作业与证据

完整作业名以 [ci-gate.mjs 的 requiredJobs](../deploy/release/ci-gate.mjs) 为准，当前为 27 个。该文件的发布门禁只接受 main 的完整成功 CI，不能直接把功能分支运行当作发布验收；本清单也不授权发布。

| 验收域 | 必查作业／范围 | 接受证据 |
| --- | --- | --- |
| 服务、协议与生产页面 | build-and-test amd64／arm64、schema | 最终提交的构建与服务测试；生产 web-dist；告警分页、用户管理、改密、归因与失败提示的真实生产包检查 |
| 原生 Agent 与服务生命周期 | linux-native、windows-agent、native-scap、native-yara | 实际平台／架构、原生工具与版本；服务启动、重启、更新／回退和动作事实；不能将交叉编译当作运行验收 |
| 双数据库与任务数据 | build-and-test、system-acceptance、reporting | SQLite／PostgreSQL 迁移、应用账号权限、报告失败回滚与重放、资产序号／失败保留、会话撤销、审计保存点及统计 |
| 集群 | cluster amd64／arm64 | 持久收件箱接收／执行边界、失败重试、会话隔离及较新资产保护；不能把 SQL 接收回执当作业务动作完成 |
| 部署与恢复 | deployment、sqlite-maintenance | 业务 `/api/ready`、核心依赖故障、身份材料与恢复结果；保持最小服务集与资源边界 |
| 外部格式与来源 | scap-resolver、baseline-upstream、vendor-advisories、opencti-native、source-trust | 对应候选的实际格式、受控来源、权限和失败保留证据；现场私有来源继续单独待验 |
