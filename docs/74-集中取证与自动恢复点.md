# 集中取证与自动恢复点

> 版本基线：v0.0.4。已按本版核对「集中取证与自动恢复点」的操作、实现引用与适用边界；历史日期及验证结果仍只对应其原始提交。版本差异见[发布说明](releases/v0.0.4.md)，全部资料见[文档索引](README.md)。

本组包含 Linux／Windows Agent 集中诊断与隔离样本采集，以及现有 Linux Compose 主机的自动成套备份。管理员在「系统管理 → 集中取证」发起采集；自动备份由 Docker 主机上的独立计划运行，不向应用容器开放 Docker socket。

## 集中采集

需要最近两分钟内在线、支持取证协议的 Agent。旧 Agent 显示不可选，升级后自动上报能力。填写用途，选择主机诊断包或已有隔离样本：

| 内容 | 实际采集范围 | 边界 |
|---|---|---|
| 诊断 ZIP | 运行时／架构／版本、资源计数、当前心跳防护状态 | 固定 `runtime.json`、`heartbeat.json`、`README.txt`，不读取原始配置、环境变量、私钥或任意日志路径 |
| 隔离样本 | 指定捕获 ID 的原始字节 | 从现有病毒发现记录选择，绑定原路径和 SHA-256；原生安全句柄拒绝替换／链接／变化的内容；不恢复、不删除隔离样本 |

每份文件最多 1 MiB，诊断 ZIP 展开总量最多 256 KiB、单条目最多 128 KiB。全平台最多 200 条请求和 64 MiB 文件字节，保存 30 天；超过配额明确失败，管理员可删除旧记录。请求十分钟超时，每台主机同时一个待完成请求；Agent 与其他批量采集共用单飞限制。

请求、元数据及实际文件在同一数据库事务保存，覆盖 SQLite／PostgreSQL；整套备份自动包含这些文件。服务端按 mTLS 主机身份、请求、指令、类型、时限、长度及 SHA-256 校验。单独 ACK 不会使文件进入「已就绪」。Agent 将未确认文件保存在私有、有界、原子替换的 outbox，重启后重传相同字节，直到收到对应提交回执；超过请求截止时间一小时后停止重传，并在下一次读取 outbox 时原子清理过期记录。离线或未运行时，磁盘副本可能留到重新连接；断线队列也可能保有待清理的副本，遵循现有 24 小时环形保留策略。

列表、样本清单、采集、删除和下载均仅管理员可访问，并重新检查当前数据库账号权限。下载使用 JWT、`no-store`、附件与二进制类型；客户端核对列表摘要、响应摘要及实际字节。记录保留下载次数、最后下载账号和时间。隔离样本只在受控分析环境中处理，浏览器不会预览或执行样本。

诊断状态仅说明采集时观察结果；没有采集成功、没有规则或没有发现均不能证明安全。诊断包不包含原始日志全文，原始日志集中检索属于后续模块。

## 自动完整恢复点

`deploy/backup_schedule.py` 复用 [成套维护](54-部署维护与成套恢复.md) 的锁、部署指纹、停机、校验、安全快照、回滚和中断恢复。支持标准 SQLite 或 PostgreSQL 17 Compose，备份数据库、完整应用数据（含取证文件／CA／JWT）及 Web TLS。每次备份短暂停止现有 web／server，再启动同一容器并验证健康。外部写入应遵守同一维护窗口。

恢复精度是**完整部署检查点**。`select` 返回不晚于指定时间的最近完整检查点及实际时间；不会把检查点之间的写入补齐。PostgreSQL 使用逻辑完整备份，不提供连续 WAL 级 PITR。这样数据库和应用文件在同一恢复边界；不把单独数据库回放称为整套恢复。

在 Linux Docker 主机使用 Python 3.10+；示例必须按实际安装路径、Compose 和环境文件调整。开启计划代表授权计划内停机，应由维护人员明确启用：

```bash
schedule=(python3 -B deploy/backup_schedule.py \
  --compose-file deploy/docker/docker-compose.lite.yml \
  --env-file deploy/docker/.env.lite \
  --state-dir /var/lib/alinksec-operations)

# 首次配置后即到期，首次 run-due 会备份；此命令本身不停止服务。
"${schedule[@]}" configure --backup-dir /srv/alinksec-backups --interval-minutes 1440 --keep 7
"${schedule[@]}" list
"${schedule[@]}" run-due
"${schedule[@]}" disable
```

PostgreSQL 替换为 `docker-compose.yml` 和 `.env`。计划与维护使用相同私有状态目录及原 Docker 部署身份。备份根目录及状态目录必须由维护账号拥有、权限 700，环境文件 600。目录中含私钥及凭据，只存放在可信受控介质，定期验证容量和介质可用性。

间隔允许 15 分钟至 7 天，保留 2 至 365 个自动检查点。停机错过的时段合并一次，不集中补做；成功后按完成时间计算下一次。失败 5、10……60 分钟后重试，输出失败退出码和脱敏错误。`--force` 立即执行，但不会绕过停用状态。不会自动处理未完成的破坏性恢复：发现维护标记时停止并要求原 `operations.py recover --yes`。

快照已封存而计划进程中断时，重启先确认原部署健康并校验快照，然后重新登记原恢复点。只有完整成功登记后才按保留数清理自动点；不清理手工快照、`pre-restore-*` 安全快照或 `.partial-*`。清理前校验所有候选，损坏会明确失败；清理中断可能留下私有孤立目录，可在人工确认后处理。

## 按时间恢复与系统调度

先只读选择并检查输出：

```bash
"${schedule[@]}" select '2026-10-24T01:00:00+08:00'

# 将 select 返回的 manifestSha256 原样填入。
# 会停机、先做当前状态安全快照，再恢复所选完整部署。
"${schedule[@]}" restore-at '2026-10-24T01:00:00+08:00' \
  --expected-manifest-sha256 '<已审核的清单摘要>' --yes
```

时间必须带时区；早于最早完整点会拒绝，所选点损坏也拒绝，不静默退到更早备份。清单摘要将执行绑定到刚审核的点，计划变化导致选中其他点时须重新审核。恢复仍要求原镜像／配置／卷／Docker engine，不能用于跨机导入或大版本降级。恢复失败自动回滚，回滚失败保留标记并尽力保持停机；恢复过程见维护文档。

`deploy/systemd/alinksec-backup.service` 与 `.timer` 是可选模板，默认仓库位于 `/opt/alinksec`、使用 SQLite 参数及 `/var/lib/alinksec-operations`。先修改服务中的实际路径和数据库参数，再配置计划并安装：

```bash
sudo install -m 644 deploy/systemd/alinksec-backup.service deploy/systemd/alinksec-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now alinksec-backup.timer
systemctl list-timers alinksec-backup.timer
journalctl -u alinksec-backup.service

# 停止自动触发时同时停用计划；备份和安全快照仍保留。
sudo systemctl disable --now alinksec-backup.timer
"${schedule[@]}" disable
```

计时器每五分钟检查一次，实际备份仍由持久化间隔决定；重启后恢复检查，不依靠应用进程。使用同一维护账号；服务默认 root，如改为专用账号，需原部署 Docker 权限及私有目录所有权。仓库仅提供模板，不会自动安装计时器或操作现有服务。

## 验证

`EvidenceIntegrationTest` 对真实 SQLite／受限 PostgreSQL 执行相同事务与权限、摘要、配额、重复结果及并发请求检查，并导出真实数据库和文件供网页验证。原生 Agent 场景在 Linux amd64／arm64、Windows amd64 执行注册、mTLS、实际进程重启、字节重传、提交回执及原生隔离导出。浏览器检查管理员角色、文件摘要、采集过程、错误与移动布局。

备份单元验证使用真实 SQLite 数据库和封存快照；完整 Compose 验证在两种数据库的独立 CI 场景执行实际自动备份、到期合并、摘要绑定恢复、整套数据及权限／CA／JWT 保留、保留策略和安全快照保留。CI 只上传验证结果，不上传整套备份、私钥、环境文件或原始部署配置。
