## R71 / P1：标准 Falco 告警不能可靠归属到真实主机

**触发与代码证据。** [KernelTelemetryService.ingestFalcoEvent](../server/alinksec-service/src/main/java/com/alinksec/service/telemetry/KernelTelemetryService.java) 不读取顶层 `hostname` 或 `output_fields["evt.hostname"]`，只在 `output_fields.nodename` 存在时查询主机。此前先用 Pod 名、容器名或 `falco-node` 作为 agentId。标准输出只有 hostname 时，即使平台存在匹配主机也不会执行该关联查询；空/null Pod 字段也不能当成可信主机 ID。

**用户可见影响。** [AlertQueryService](../server/alinksec-service/src/main/java/com/alinksec/service/query/AlertQueryService.java) 的 LEFT JOIN 仍可能展示告警，但真实主机筛选无法命中、主机名/IP 缺失；[ComplianceReportService](../server/alinksec-service/src/main/java/com/alinksec/service/report/ComplianceReportService.java) 的主机 JOIN 会排除无归属记录。依赖真实 agentId 的响应也不能据此证明可执行。数据库约束造成直接入库失败的场景需单独验证，不宣称所有环境均返回成功。

**为何原测试未覆盖。** [KernelTelemetryServiceTest](../server/alinksec-service/src/test/java/com/alinksec/service/telemetry/KernelTelemetryServiceTest.java) 的成功样例主动加入 `output_fields.nodename`，只能证明定制输入路径，不能证明标准 Falco 输出兼容。

**修复与验收。** 将探针实例、真实宿主机、Pod/容器身份分开，通过已登记映射绑定主机；兼容来源字段但拒绝凭任意重名直接归属，未绑定事件显示明确状态并禁止主机响应。用仅顶层 hostname 的官方结构、探针运行在容器内、两个集群同名 Pod、同名主机、缺失/null 字段逐项验证告警主机筛选、报表和响应目标。该项是 G02/R15 的具体接入断点，修好字段解析不等于探针安装与来源可信已经完成。

## R72 / P1：Elkeid 网络、DNS、文件等事件被压成进程告警并丢字段

**触发与代码证据。** [ingestElkeidEvent](../server/alinksec-service/src/main/java/com/alinksec/service/telemetry/KernelTelemetryService.java) 统一设置 `type="process"`，detail 仅保留 data_type、exe、pid、ppid、uid、nodename、pid_tree、argv 等通用字段，不保留原对象。即使桥接器已提供完整 JSON，42 的 dip/dport/sip/sport/res、601 的 query、602 的 file_path、603 的 ko_file、604 的 old_uid/res 仍会丢失。

**用户可见影响。** 用户知道发生了一条 Hook 事件，却看不到连到哪里、查了哪个域名、创建了哪个文件或是否成功；这些字段不在存储对象中，后续单改页面无法找回。[KernelTelemetryDetail](../web/src/components/KernelTelemetryDetail.vue) 也没有类型专有字段展示。相同进程同 data_type 的事件还沿 [SecurityEventService](../server/alinksec-service/src/main/java/com/alinksec/service/alert/SecurityEventService.java) 的进程指纹合并，目标差异无法作为独立证据；聚合原始证据问题继续关联 R35。

**修复与验收。** 建立按 data_type 的有版本映射：保留事件来源/类型、目标对象、结果、时间及容器上下文，按 R39 脱敏和限制大小；未知类型明确标识，不伪装成已识别攻击。对 connect 成功/失败、两个不同目的地址、DNS 两个域名、文件创建和凭据变化分别走入库→API→详情→检索，验证关键字段不丢失、类型正确、聚合仍保留证据。Driver 到 JSON 的转换器必须独立验收，不用手写 JSON 冒充原生桥接成功。

## R73 / P1：Falco 接入示例的自定义 Token Header 未接通

**触发与代码证据。** [接入文档 90 §3.1](90-内核与eBPF遥测接入规范.md) 配置 `http_output.custom_headers` 并直连本项目。所查 Falco 0.45.0 的 configuration.cpp 不读取此项，outputs_http.cpp 只按输出格式加入 Content-Type，没有把该配置加入请求头；0.40.0 同样如此。User-Agent 写为 `falco/0.45` 不会增加这个功能。

**用户可见影响。** 当平台已启用遥测且配置非空 falco-secret 时，[TelemetryController](../server/alinksec-gateway/src/main/java/com/alinksec/gateway/rest/TelemetryController.java) 要求 X-Falco-Token 或 Bearer Token；沿该直连步骤无法携带凭据，不能完成鉴权投递。未知配置键是被忽略、警告还是启动拒绝要在所选二进制上验收，不能推断唯一启动行为。curl 手动加头成功也不能证明 Falco 客户端已经接通。

**修复与验收。** 为固定版本提供真实可工作的中继/适配器，或采用经过实现和验证的来源认证链，并明确证书校验、重试与失败可见性。不要靠清空密钥解决功能问题。用无害规则事件从真实 Falco 发出，确认接收端实际得到所需头；分别验正确/错误密钥、轮换、重启后配置保留、服务端拒收和重新投递，最后验证告警可见。与 R01 的服务端鉴权边界分别验收。

## R74 / P2：宿主机和未知事件被错误展示为确定的容器状态

**触发与代码证据。** Falco 字段合同以 `container.id="host"` 表示宿主机事件；容器元数据也可能延迟或缺失。[ingestFalcoEvent](../server/alinksec-service/src/main/java/com/alinksec/service/telemetry/KernelTelemetryService.java) 只要有 container.id 或 container.name 键，就保存 `in_container=true`，因此 host 哨兵甚至 null 键都可能被判为容器事件。Elkeid 路径反而没有设置 in_container；[KernelTelemetryDetail](../web/src/components/KernelTelemetryDetail.vue) 将任何假值/缺字段一律展示为“宿主机”。

**用户可见影响。** Falco 的宿主进程显示“容器内部”，Elkeid 的容器事件或未知状态可能显示“宿主机”，排查对象被误导。此项只确认归一化与展示错误，不声称当前响应规则必然使用了这个标记。

**修复与验收。** 使用 host/container/unknown 三态，正确处理 host、空值、null、缺字段与来源能力；容器和主机身份分别保存。以 `{"container.id":"host","container.name":"host"}`、真实容器 ID、只缺名称、全部缺字段、null 字段及 Elkeid 缺命名空间证据为输入，逐层验证存储和 UI，不用字段“存在”代替语义判断。

## R75 / P1：普通 Elkeid 采集事件直接成为风险告警，缺少检测判定层

**触发与代码证据。** Elkeid Driver 包含常规 execve/connect 等采集 Hook；事件到达不等于已判为攻击。[ingestElkeidEvent](../server/alinksec-service/src/main/java/com/alinksec/service/telemetry/KernelTelemetryService.java) 对任何含 data_type 的非空对象都会构造 process 安全事件并调用 onEvent；59 固定级别 2，356/603 固定级别 4，未知类型也走默认 2，没有执行检测条件、结果核验或正常业务例外。

**用户可见影响。** 正常命令执行也进入“可疑进程”告警；合法 memfd 使用、模块加载不经上下文判断就形成高级别告警。新告警进入通知和 [ResponseAutomationService](../server/alinksec-service/src/main/java/com/alinksec/service/response/ResponseAutomationService.java) 评估：若用户已配置匹配的启用/批准规则，可能对正常行为发起处置。没有匹配规则时不能写成“默认自动隔离”，未知类型也不能伪装成已覆盖的检测种类。

**修复与验收。** 分开原始遥测、已匹配检测、运行故障三类数据；给明确检测规则配置条件、正常例外、版本及证据，对真正检测型 Hook 保留其语义，不将所有 Hook 一刀切降级。正常 shell、正常网络连接、合法模块维护和受控命中样例成对验收；未知 data_type 不应形成已识别威胁，普通原始事件不触发安全响应。R72 负责保全数据，R75 负责何时形成风险，两项不能互相替代。

## 已有事项补充与排除结论

- **G12 追加参考与验收。** Wazuh 明确区分目录监控和属性/排除配置。本项目 [fileMonitor.update/checkFile](../agent/internal/guard/filemon.go) 不递归，目录对象进入 non_regular；默认 PR-0002 只有五个明确文件，不包含 cron.d 或自动展开所有用户 authorized_keys。文档 84 C01 的目录/用户路径“已实现”不能作为覆盖证据。后续以目录中新建/修改文件、子目录、用户目录变化、排除规则和合法维护基准刷新建立用例，仍归 G12，不新增重复缺陷。
- **排除实时查毒批次截断推断。** virusSweep 虽有 200 条上限，但当前生产调用 [fileevents.go](../agent/internal/guard/fileevents.go) 每次只传一个路径；eventPending 和 virusRecovery 保留未完成工作并有启动/溢出恢复遍历。不能据函数中切片截断就断言“第 201 个文件永远漏检”。这里只排除该推理，不证明所有引擎失败或文件洪峰场景都通过。
- **U09 的 FIM 持久化旧标题已收敛。** [saveBaseline/writePrivateAtomic](../agent/internal/guard/filemon.go) 使用临时文件、Sync、Rename，监控方法持有互斥锁；“完全没有原子替换和并发保护”不成立。JSON/BIN 两文件跨崩溃一致性仍可专项检查，不能据已有单文件保护直接关闭全部恢复事项。
- R59–R68 正文的修复/关闭条件恢复为具体待验要求；只将总表作为索引，不能让“见正文”替换正文自身的修复要求。
