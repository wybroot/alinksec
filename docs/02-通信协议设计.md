# ALinkSec 通信协议设计（gRPC / Protobuf）

> 适用版本：v0.0.1；更新日期：2026-10-02。下文为协议设计与示例；当前完整字段、枚举和 RPC 以 [`proto/agent.proto`](../proto/agent.proto) 为准。

v0.0.1 注册服务使用平台 CA 验证服务端，注册后所有 Channel 报告与 ACK 均按客户端证书绑定 Agent 身份，拒绝跨主机上报。默认内置策略仅告警；Linux 文件与 SSH 策略见 [实际配置](11-登录与文件防护.md)。协议 fixture 测试和实际 Agent 联动的覆盖差异见 [验收记录](12-原生Agent本机验收记录.md)。
> 日期：2026-08-25
> 配套：`proto/agent.proto`（服务端与 Agent 共用同一份源文件生成 Java/Go stub）

## 1. 协议总览

| 通道 | 服务 | 模式 | 用途 |
|------|------|------|------|
| 注册通道 | `EnrollService.Enroll` | 一元 RPC | 首次安装换取 Agent 身份与客户端证书 |
| 主通道 | `AgentChannel.Channel` | **双向流** | 上行 Report / 下行 Command，单连接复用 |

- 传输：gRPC over HTTP/2，**mTLS 双向认证**。
- 端口：`9443`（Nginx/网关 TLS 终结或直通，私有化部署直通更简单）。
- 消息头：所有 Report 携带 `agent_id`；Agent 身份以 mTLS 证书 CN 为准，服务端校验 `agent_id == 证书CN`，**不信任消息体自报身份**。

## 2. proto 定义

完整 v0.0.1 协议直接维护于 [proto/agent.proto](../proto/agent.proto)，本文不再复制早期 schema 示例，避免字段或枚举漂移。服务端 Maven 按构建平台生成 Java/gRPC 类型；Agent 对应类型位于 [internal/proto](../agent/internal/proto)。

注册 RPC 建立初始身份和客户端证书；随后通过双向流传递 Command 与 Report。业务报告包括心跳、资产、基线、扫描、防护事件、病毒与修复结果、日志、指标及 ACK。新能力必须沿用既有字段号和证书绑定身份，不能根据上报的任意 agent_id 变更所属主机。

## 3. 指令可靠性设计

以下超时、批次和容量描述为可靠性设计目标，实际任务状态及重试行为以服务端调度器、Agent ACK 和对应测试为准。v0.0.1 已验证实际下发、失败回写、证书身份校验与断线补传；没有规模压测结论。

### 3.1 状态机与超时重推

```
PENDING（已入库）→ SENT（已写入 stream）→ RECEIVED（Agent ACK）
    → RUNNING（长任务 ACK）→ DONE / FAILED（终态）
```

- gateway 对 `SENT` 状态指令启动 30s 定时器，未收到 `RECEIVED` 重推，最多 3 次，之后置 `FAILED(timeout)`。
- 长任务（基线核查/扫描）由 Agent 阶段性上报 `RUNNING` + 进度百分比（message 字段）。

### 3.2 幂等

- Agent 收到指令先查本地 `cmd_id` LRU（容量 1000）：
  - 已存在且非终态 → 仅重发上次 ACK；
  - 已存在且终态 → 重发终态 ACK，**不重复执行**；
  - 不存在 → 执行。
- `RptAck` 与 `Report` 走同一上行流，天然保序。

### 3.3 指令风暴防护

任务范围 > 200 台时分批下发（每批 200，间隔 5s，可配置），避免 gateway 瞬时写出压力与 Agent 同时执行导致的采集尖峰。

## 4. 上报链路与背压

| 上报类型 | 路径 | 说明 |
|----------|------|------|
| heartbeat | gateway 直处理 | 更新心跳与在线状态，比对 policy_version |
| metrics | 服务端 → VM（`/api/v1/import/prometheus`） | 标准模式写入，轻量模式默认关闭 |
| asset / baseline / scan / security_event / virus / fix / log | gateway 身份校验 → 业务服务 → PostgreSQL / SQLite | 业务报告直接分发入库，不依赖 MQ |
| ack | gateway 直处理 | 更新 t_command 状态 |

- **批量上报**：Agent 侧非实时数据（资产快照、基线结果）打包发送，单条 Report 上限 4MB（gRPC 默认消息上限调优为 8MB）。
- **业务补传**：报告持久化到 Agent 本机 `queue/pending.jsonl`，断线及进程重启后仍可补传；结果处理使用业务任务、报告身份及指令所属主机约束幂等。
- **资源控制**：Agent 离线队列有时间和大小上限，默认补传速率 100 msg/s；外部 Redis 限流为后续扩展规划。

## 5. 断线重连

```
连接断开 → 指数退避重连（1s,2s,4s,...上限 30s，加 ±20% 抖动）
重连成功 → 上行 RptHeartbeat（携带 last_report_id）
        → 服务端检查 policy_version，不一致则下发 CmdPolicySync
        → Agent 开始补传离线队列（限速：100 msg/s，避免冲击）
```

- 重连期间 guard 引擎持续运行（本地策略），事件写入离线队列。
- 心跳超时判定（服务端 30s）与 Agent 重连退避（上限 30s）需匹配，避免误判在线。

## 6. 安全机制

| 机制 | 实现 |
|------|------|
| 双向认证 | 服务端内置 CA 签发 Agent 证书；`CN=agent_id`；证书有效期 10 年（私有化场景换证成本高） |
| 身份校验 | gateway 从 TLS 层取证书 CN，与消息 `agent_id` 比对，不一致断连并记录审计 |
| 注册防重放 | enroll_token 一次性 + nonce 落库去重 |
| 指令防伪造 | 指令仅可能来自 mTLS 通道；`CmdProtectAction` 全量审计 |
| 吊销 | Agent 删除/禁用 → t_agent 状态变更 → gateway 拒绝相应身份连接 |
| 协议演进 | proto 预留字段号；版本协商依赖 agent_version + 心跳上报，不单独做协议握手 |
