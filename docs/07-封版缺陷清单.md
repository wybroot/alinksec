## 3. P0 封版阻断项

### REL-001 Linux Docker/干净 CI 无法生成 protobuf

- 证据：`deploy/docker/Dockerfile.server:6` 只复制 `server/`；`server/alinksec-proto/pom.xml:108`、`:111`、`:115` 又依赖仓库根的 `tools/protoc/bin/protoc.exe` 与 `proto/agent.proto`。POM `:64`、`:66` 固定 Windows 生成器，而构建镜像为 Linux。`tools/` 还被 `.gitignore:49` 排除，发布打包脚本 `docs/06-部署文档.md:121-125` 未包含 `proto/`。
- 影响：干净的 GitHub Ubuntu CI、Linux Docker builder 与正式发布包均无法构建服务端镜像。
- 修复要求：移除对本机 `protoc.exe` 的依赖；按构建平台下载/使用 `protoc` 与 `protoc-gen-grpc-java`，Docker 构建上下文显式包含受版本控制的 `proto/agent.proto`。同步修正发布包脚本。
- 验收：在无 `tools/` 的干净 Linux checkout 中，`docker compose build server` 成功；CI 增加同等构建检查并通过。

### REL-002 登录成功后抛 500

- 证据：`server/alinksec-gateway/src/main/java/com/alinksec/gateway/rest/AuthController.java:52` 将 `Map.of(...)` 传给签名方法；`server/alinksec-common/src/main/java/com/alinksec/common/util/JwtUtil.java:21` 对该 Map 执行 `put("exp", ...)`。
- 影响：凭据正确时抛出 `UnsupportedOperationException`，管理端无法获得 JWT。
- 修复要求：签发 JWT 时不得修改调用方传入的 Map；在方法内复制为可变 Map 后再写入 `exp`，或由调用方传入可变 Map。
- 验收：补充 AuthController/JwtUtil 自动化测试；正确密码登录返回 `code: 0`、JWT 可通过鉴权，错误密码仍返回预期业务错误。

### REL-003 Agent 可伪造其他 Agent 上报和 ACK

- 证据：`server/alinksec-gateway/src/main/java/com/alinksec/gateway/rpc/AgentChannelImpl.java:63-65` 在首条认证后无条件接受后续 Report，并在 `:54` 使用 Report 自带的 `agent_id` 分发。`ReportDispatcher.java:69-72` 丢弃流身份；`CommandRepository.java:81-93` 只以 `cmd_id` 更新 ACK。
- 影响：持有任一合法客户端证书的 Agent 可伪造其他主机资产、事件、心跳，或伪造其他主机指令的完成状态。
- 修复要求：每条 Report 的 `agent_id` 必须等于 mTLS CN/流内 `authenticatedAgentId`；ACK 更新必须同时约束 `agent_id` 与 `cmd_id`。
- 验收：补充 gRPC 集成测试，使用 Agent A 的证书发送 Agent B 的 Report/ACK，服务端必须拒绝且 B 的数据与指令状态不变。

### REL-004 Schema CI 表数量断言错误

- 证据：`.github/workflows/ci.yml:56-57` 断言 public schema 为 35 张表；`deploy/sql/001_init.sql` 实际包含 38 个 `CREATE TABLE IF NOT EXISTS`，包括 `:893`、`:908`、`:920` 的 M4 表。
- 影响：schema job 独立执行时必然失败，发布门禁失效。
- 修复要求：将断言更新为当前受支持 schema 的准确期望，并在导入命令添加 `psql -v ON_ERROR_STOP=1`。
- 验收：GitHub Actions schema job 成功；故意插入非法 SQL 时 job 必须失败。

## 4. P1 高风险项

### REL-005 审计日志泄漏 webhook 凭据

- 证据：`AuditFilter.java:57-65` 保存非认证请求体原文；`NotifyChannelController.java:32-39` 接受带 token 的 `webhookUrl`；`AuditController.java:23-28` 返回 `body_digest`，而 `JwtAuthInterceptor.java:68-76` 对读操作不限制 viewer。
- 影响：低权限 viewer 可从审计记录恢复通知机器人或 webhook 凭据。
- 修复要求：审计仅保存不可逆摘要或字段白名单；明确将审计查询限制为管理员，历史敏感审计记录需清理或脱敏。
- 验收：创建/修改带 secret 的通知通道后，数据库和 `/api/audit/logs` 均不得返回 URL、token 或其可还原片段；viewer 请求审计接口返回 403。

### REL-006 漏洞软件包修复入口永远不可用

- 证据：`web/src/api/index.js:427-452` 聚合漏洞时丢弃 `id` 与 `agent_id`，未组装 `findings`；`web/src/views/Vuln.vue:231-250` 没有 `findings` 时拒绝创建修复任务。
- 影响：产品已展示的单项与批量软件包修复功能永远不下发任务。
- 修复要求：保留每个待修复 finding 的 `{ agentId, findingId }`，按状态过滤后传给修复任务接口。
- 验收：至少两台主机的同一 CVE 可创建单项和批量修复任务，服务端与 Agent 均收到正确的 finding 列表。

### REL-007 主机隔离状态不持久化

- 证据：`Hosts.vue:256-259` 只在前端立即改为 `isolated`；`HostsController.java:151-166` 仅下发命令；`AgentRepository.java:72-78` 后续心跳把状态重置为在线。
- 影响：页面刷新后隔离主机被误报在线，解除隔离入口消失，安全处置状态不可审计。
- 修复要求：将在线状态与隔离状态拆分持久化；仅根据 Agent ACK 更新隔离状态，并为失败、超时、解除隔离定义状态机。
- 验收：隔离、刷新、心跳、服务重启、解除隔离全流程状态一致，指令 ACK 与审计记录可追溯。

### REL-008 防护开关只改前端状态

- 证据：`Hosts.vue:38` 与 `Protect.vue:5` 仅显示成功消息；`web/src/api/index.js:646-650` 将卡片状态硬编码为开启；后端没有 `protect_enabled` 或引擎启停写接口。
- 影响：用户认为已启用/停用实时防护，实际策略与 Agent 行为未改变。
- 修复要求：要么实现受 RBAC 保护、可审计、可 ACK 的策略写接口，要么移除不可用开关并以只读状态展示。
- 验收：操作后刷新页面、服务端策略快照和 Agent 生效状态三者一致；无后端能力的控件不得呈现为可编辑。

### REL-009 生产数据库权限和端口暴露过宽

- 证据：`deploy/docker/docker-compose.yml:9` 的 PostgreSQL bootstrap 用户与 `:45` 的应用 `PG_USER` 相同，默认为 superuser；`:61-62` 与 `:79-81` 将管理和注册端口发布到全部网卡。部署清单 `deploy/部署检查清单.md:40` 的要求与 `:83` 的无源地址限制命令不一致。
- 影响：应用被攻破时可获得数据库超级用户权限；管理面和注册码接口可能暴露到非预期网络。
- 修复要求：分离初始化/迁移账户和最小权限应用账户；为端口绑定、DOCKER-USER 或上游防火墙提供明确的源网段限制方案。
- 验收：应用账户无建角色、执行程序等超级权限；非管理网和非受管主机无法连接 8443/9443。

### REL-010 HOST_IP 缺失时静默生成错误 SAN

- 证据：`docker-compose.yml:55`、`:59` 在 `HOST_IP` 未设置时回退为 `alinksec-server`，而 `.env.example:5` 只是占位 IP。
- 影响：首次启动可能生成不包含真实接入地址的证书和下载 URL，补救需要重建证书卷并使既有 Agent 证书失效。
- 修复要求：将 `HOST_IP` 改为 Compose 必填变量，并在首次启动前验证为允许的 IP 或 DNS 名称。
- 验收：缺失或占位值时 `docker compose config -q`/启动脚本失败；正确地址出现在服务端证书 SAN 与 Agent 下载 URL。

### REL-011 缺少已有数据库升级路径

- 证据：`deploy/sql/001_init.sql:1` 明确仅适用于空库；Compose 仅将其挂载到 PostgreSQL 首次初始化目录（`docker-compose.yml:14-16`）。文档 `docs/06-部署文档.md:637` 也确认已有卷不会自动升级。
- 影响：升级已有环境时缺表/缺列会在运行期失败，无法安全回滚。
- 修复要求：引入版本化迁移机制或提供每个版本可重复执行的升级脚本、schema version 与前置检查。
- 验收：从上一受支持版本的 PG 备份恢复后可执行升级，所有迁移可重复运行，应用启动、回滚和核心接口均通过。

### REL-012 Docker 构建不可复现且 CI 未覆盖镜像启动

- 证据：`Dockerfile.server:12` 硬编码 `0.1.0-SNAPSHOT.jar`；`.dockerignore` 未排除 `server/**/target`，镜像内也未 `clean` 构建；`.github/workflows/ci.yml` 没有 Docker/Compose build 或启动验证。
- 影响：版本号升级、残留 class 或容器编排错误可能在正式服务器才暴露。
- 修复要求：使用稳定最终产物名或显式版本参数，排除服务端 target，镜像内执行 clean build；CI 加入 Linux Docker build、Compose 配置校验和最小启动/健康检查。
- 验收：连续两次从干净 checkout 构建产生可启动镜像；版本号变更无需修改 Dockerfile；CI 覆盖 image build 与健康接口。

## 5. P2 发布前应处理项

### REL-013 主机分页与漏洞展示数据错误

- 证据：`web/src/api/index.js:286-287` 固定读取前 100 台，`HostsController.java:45-50` 也限制为 100，`Hosts.vue:15,54` 的分页器未驱动请求。漏洞页读取不存在的 `cve_fixed`（`index.js:437`），后端返回 `fixed_version`（`VulnQueryService.java:45-47`），并且默认查询排除已修复项（`:25-29`）。
- 影响：超过 100 台主机无法管理；目标修复版本显示为空，修复率恒为零。
- 修复要求：实现服务端分页与前端页码联动；对齐漏洞字段，并提供统计所需的已修复数据或独立统计接口。
- 验收：101 台以上环境可查询、操作任意页主机；修复版本和修复率与数据库数据一致。

### REL-014 ECharts 生产依赖存在已知 XSS 公告

- 证据：`web/package-lock.json:1088` 锁定 `echarts@5.6.0`。`npm audit --package-lock-only --omit=dev --registry=https://registry.npmjs.org` 报告 `GHSA-fgmj-fm8m-jvvx`，影响范围 `<6.1.0`，修复版本为 `6.1.0`。
- 影响：存在已公开的 moderate XSS 风险；升级是 major 版本，需回归图表渲染。
- 修复要求：评估并升级至安全版本，完成受控数据和恶意标签数据的图表回归。
- 验收：生产依赖 audit 无该公告，核心仪表盘/大屏图表通过回归。

### REL-015 TLS 排障命令无效

- 证据：`docs/06-部署文档.md:673` 使用 `docker compose down server`，而 `down` 不接受服务名。
- 影响：证书 SAN 出错时，运维人员按文档无法执行恢复步骤。
- 修复要求：改为明确的停服、删除目标容器/卷、重启顺序；保留已签发 Agent 证书失效警告。
- 验收：在隔离测试环境按文档可完成 SAN 修复，并能重新接入测试 Agent。
