# 部署维护与成套恢复

`deploy/operations.py` 为现有单机 Compose 部署提供状态检查、停机备份、离线校验、成套恢复和中断恢复。支持 Linux Docker 主机上的 Python 3.10+，以及项目标准 SQLite 或 PostgreSQL 17 部署；Linux amd64、arm64 的应用场景在独立 CI runner 验证。本机低内存验证仍串行执行。

## 快照范围与条件

| 内容 | SQLite | PostgreSQL |
|---|---|---|
| 业务库 | 停止应用后归档数据库、WAL 和同目录文件 | 停止应用后执行自定义格式 `pg_dump` |
| 应用数据 | 完整 `/app/data`：CA、证书、持久化 JWT、特征库、补丁与 Agent 物料等 | 相同 |
| Web TLS | 完整 `/app/web-tls` | 相同 |
| 配置记录 | 环境文件、Compose 原文、实际容器环境和镜像 ID | 相同 |
| 恢复约束 | 原 Docker engine、项目、卷名、实际镜像 ID 和运行环境一致 | 还绑定 PostgreSQL 数据卷，保留现有集群角色 |

只接受标准本地 Docker 命名卷；额外可写挂载、绑定挂载、自定义卷驱动/选项及 PostgreSQL 自定义 tablespace 会被拒绝。server、web 必须各有一个已运行且未暂停的容器；工具不会替用户启动原本停用的部署，不构建、拉取或替换镜像，也不隐式启动依赖。

快照是敏感材料，包含私钥和凭据。快照根目录及状态目录要求当前维护用户拥有、权限 `700`；环境文件要求 `600` 或更严格，快照文件以仅当前用户可读写的权限生成。将快照存放在受控介质；CI 只保留脱敏结果，不上传原始快照。

VictoriaMetrics 时序卷、主机配置、外部数据和 PostgreSQL 集群全局角色不在快照中。本工具执行原部署恢复，不提供新机灾备导入、跨数据库互转、连续 WAL 级 PITR、集群角色重建或数据库大版本降级。自动调度与完整检查点时间选择见 [集中取证与自动恢复点](74-集中取证与自动恢复点.md)。其他进程、维护主机及管理员写入不受应用停机约束，应统一维护窗口。

## 命令

在发布目录根执行。SQLite 示例：

```bash
chmod 600 deploy/docker/.env.lite
mkdir -p -m 700 backups
maintenance=(python3 -B deploy/operations.py \
  --compose-file deploy/docker/docker-compose.lite.yml \
  --env-file deploy/docker/.env.lite \
  --state-dir .operations/sqlite)

"${maintenance[@]}" status
"${maintenance[@]}" check
"${maintenance[@]}" backup backups/before-maintenance
python3 -B deploy/operations.py verify backups/before-maintenance

# 确定需要恢复时：会停机并先保存当前状态的安全快照。
"${maintenance[@]}" restore backups/before-maintenance --yes
```

PostgreSQL 改用 `--compose-file deploy/docker/docker-compose.yml --env-file deploy/docker/.env --state-dir .operations/postgres`。每套部署固定使用一个状态目录，保留它直到维护完成。较大备份可显式设置全局 `--timeout`，每个 Docker 命令默认最多 180 秒，上限 3600 秒。

`status` 只输出项目、模式、实际镜像 ID、容器状态、部署指纹与是否需要中断恢复，不输出环境变量。`check` 检查现有服务状态、卷、并发访问和应用健康；成功不表示新版本已具备升级条件。两条命令不修改服务运行状态，但会建立私有状态标识和维护锁。

`verify` 不连接 Docker，检查文件集合、大小、SHA256、归档路径/类型和部署元数据。SQLite 会在私有临时目录重建数据库与 WAL 并检查完整性；PostgreSQL 离线检查格式头，维护时另外用原客户端检查目录与数据库身份，完整可恢复性以实际恢复及应用检查为准。摘要不证明来源真实性；只恢复自己信任的快照，PostgreSQL 归档中的 SQL 会由数据库管理员执行。

## 停机、回滚与中断

备份先写入持久状态，停止 web、server 并确认停写，然后保存两个数据卷和业务库；写入并同步全部文件和清单后，原子发布快照目录，再启动原容器并检查健康。已有目标目录不会覆盖；失败的临时目录不作为指定目标发布，保留供排查。

恢复在停机前验证目标快照及部署指纹，停机后先制作 `pre-restore-<随机编号>` 安全快照，再替换两个卷的内容及数据库。成功输出包含目标与安全快照位置。后产生的文件和表也会移除，避免旧数据混入。PostgreSQL 重建整个业务库，并恢复数据库 ACL、注释及数据库/角色在该库中的设置；现有集群角色不被删除或改写。

卷清理由当前 server 镜像的短时 helper 执行：64 MiB 内存、96 MiB 内存加 swap、1 CPU、32 PID、禁用网络、只读根文件系统、移除默认 capabilities，只补充 `DAC_OVERRIDE`。内容经 Docker 归档接口读写，保留普通文件/目录的数字 UID、GID、权限及时间；不承诺 ACL、扩展属性或 SELinux 标签保留。链接、设备、FIFO、稀疏文件、特殊权限和扩展归档属性被拒绝。每卷最多 100000 项，路径最多 4096 字节及 64 层。

使用 tar 标准输入恢复时不传 `docker cp -a`：Docker daemon 的 `copyUIDGID` 会套用容器配置的用户。真实卷验证确认当前方式保留源归档的 `1001:1001 / 640`，见 [Moby 实现](https://github.com/moby/moby/blob/master/daemon/archive_unix.go)。

服务恢复或健康检查失败会自动尝试原安全快照。回滚也失败时保留状态并尽力停止 server/web，不删除安全快照。若 Docker 本身不可用，工具可能无法完成停机，需人工确认容器状态。健康探针在 Nginx 内检查 HTTPS 到应用的路由及业务成功码，不能代替从外部网络验证 CA、SAN 和访问控制。

SIGTERM/SIGINT 会进入失败处理；SIGKILL、断电等无法清理的中断保留 `pending.json`。不要直接删除状态标记或手工启动部分恢复的应用，使用原命令参数恢复：

```bash
"${maintenance[@]}" recover --yes

# 安全快照不可用、且已经人工选定另一份可信快照时：
"${maintenance[@]}" recover --snapshot backups/before-maintenance --yes
```

显式备用快照同样必须匹配原部署。恢复本身失败仍保留标记并尽力停机，可以修正故障后重试。并发锁按本机维护用户、Docker engine 和受保护卷生成，修改 `--state-dir` 无法绕过；跨维护用户/主机不提供分布式锁。维护期间不要并行运行旧 SQLite 脚本、数据库客户端或其他写卷工具。

## 升级前检查与人工回退

1. 按[发布流程](13-版本发布流程.md)核对完整 CI、发布清单、校验和及镜像 digest，保留旧发布目录、原环境文件和实际镜像。
2. 对当前部署执行 `check`、`backup`、`verify`，并在隔离部署演练业务、CA、JWT、物料和权限的恢复。快照绑定原 engine，不可直接送到另一 engine 自动恢复；隔离环境应对自己的快照演练。
3. 根据目标版本迁移说明执行升级；本工具不更换镜像、运行新迁移或授权发布。没有特定历史版本升级演练时，只声明已验证的恢复能力。
4. 升级失败时先停止应用，按目标版本的回退条件恢复旧发布物、原镜像和环境，并保留命名卷；确认原配置可满足指纹后，使用旧快照恢复业务库和两个应用卷。新应用或配置未退回时会拒绝旧快照，不会把旧库直接交给新应用。

常规 `restore` 也要求操作前应用已经健康运行，因此上一步只适用于退回原发布物后仍能健康启动的部署。若新库结构或现有损坏数据导致旧应用无法启动，必须使用该版本专门验证的离线恢复方案；本工具不提供这种冷恢复入口。不要伪造维护状态来绕过检查；`recover` 仅处理工具自身已记录的中断操作。

PostgreSQL 的归档恢复及全局对象边界见官方 [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html)、[pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html)。旧 `sqlite-maintenance.sh` 仍提供数据库单项维护，不具备本节的应用数据配套恢复能力。

## 验证入口

`deploy/tests/test_operations.py` 覆盖两种数据库的部分恢复、停机/复制失败、回滚失败与重试、显式备用快照、健康失败、并发锁、WAL、摘要/部署不符和危险归档。`operations-volume-local.py` 实测归档与数字属主/权限；`operations-postgres-local.py` 在 PostgreSQL 与 helper 之间串行切换，实测库重建、删除多余表和权限/设置保留。

完整 `operations-smoke.py` 只允许一次性 GitHub runner：SQLite/PostgreSQL、Linux 双架构逐一验证实际应用、持久 JWT、CA、TLS、物料、权限、坏摘要停机前拒绝、首次卷恢复后真实 SIGKILL 与重试，以及无效 CA 导致启动失败后的自动回滚。原始快照和凭据不进入产物。
