# ALinkSec 版本发布流程

本文描述当前分支的双架构发布流程。发布目标为 GitHub `wybroot/alinksec` 和 Docker Hub `wangyanbiao/alinksec`。ARM64 尚未发布，已有 v0.0.1 为 amd64 基线；下次发布先递增版本，不覆盖 v0.0.1 标签或镜像。

默认入口为英文 [README](../README.md)，中文入口为 [README-cn](../README-cn.md)，两版互相切换；发布包携带两版完整文档。

## 产物

| 产物 | 地址或名称 |
| --- | --- |
| 服务端，Linux amd64 + arm64 | `wangyanbiao/alinksec:server-v<VERSION>` |
| Web，Linux amd64 + arm64 | `wangyanbiao/alinksec:web-v<VERSION>` |
| SQLite 维护工具，Linux amd64 + arm64 | `wangyanbiao/alinksec:sqlite-maintenance-v<VERSION>` |
| 源码、部署文件和全部文档 | `alinksec-v<VERSION>.tar.gz` |
| Linux amd64 原生 Agent | `alinksec-agent-linux-amd64` |
| Linux arm64 原生 Agent | `alinksec-agent-linux-arm64` |
| Windows 原生 Agent | `alinksec-agent-windows-amd64.exe` |
| 产物 SHA256 | `SHA256SUMS` |
| 提交、完整 CI、资产校验与镜像 digest | `release-manifest.json` |

三个组件使用同一个 Docker Hub 仓库的独立标签，不发布无组件名的 `latest` 或 Agent 容器。`<VERSION>` 替换为 `VERSION` 文件内容。组件版本标签为包含 `linux/amd64` 和 `linux/arm64` 的镜像索引，Docker 自动选择本机架构；带 `-amd64` / `-arm64` 后缀的标签用于原生构建及冒烟。`release-manifest.json` 的 `images[].digest` 记录索引摘要，`images[].platforms` 记录各架构实际验证的镜像摘要。正式部署可用其中的 `repository@sha256:...` 覆盖 Compose 的 `ALINKSEC_*_IMAGE`。

ARM64 源码构建、安装与支持边界见 [ARM64 部署](14-ARM64支持.md)。CI 使用 [GitHub 原生 ARM runner](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)，仓库为公开仓库；迁移仓库时需确认相应 runner 可用。

ARM64 改动 `bb8cf91` 的[开发分支 CI](https://github.com/wybroot/alinksec/actions/runs/37026819693)四个作业已全部通过，三个 Agent 成品的平台、源码提交和 SHA256 已复核，详见 ARM64 文档的验收记录。此结果用于合并审查；正式发布仍要求版本递增后同一 `main` 提交的完整 CI，不复用开发分支结果，也不覆盖已有 v0.0.1。

## 仓库配置

在 GitHub Settings → Secrets and variables → Actions 配置：

- `DOCKERHUB_TOKEN`：有 `wangyanbiao/alinksec` 推送权限的 Docker Hub token。
- 也兼容已有 `DOCKERHUB_PASSWORD`，建议其中保存访问 token；若两个名称都存在，优先使用 `DOCKERHUB_TOKEN`。
- `DOCKERHUB_USERNAME`：可选，必须为 `wangyanbiao`，未设置时使用该值。

GitHub Release 使用工作流自身的 `GITHUB_TOKEN`，发布作业声明 `contents: write`；CI 查询和附件下载声明 `actions: read`。不需要把 GitHub 或 Docker Hub 凭据写入源码、Compose、日志或发布包。

## 发布顺序

1. 更新 `VERSION`、六份 Maven POM、Agent 产品版本、前端 `package.json/package-lock.json`、两份 Compose 的默认镜像标签和发布说明。
2. 串行执行本机可安全运行的检查。`node deploy/release/check-version.mjs` 检查版本和默认镜像；`node --test --test-concurrency=1 deploy/tests/release-*.test.mjs` 验证发布门禁、二进制架构与镜像索引。低内存主机遵守仓库 `AGENTS.md`，重构建有内存监控，前端构建前暂停后端。
3. 提交并推送到 `main`，等待该提交的完整 `CI` 通过。`windows-agent`、`build-and-test (amd64)`、`build-and-test (arm64)`、`schema` 四个作业必须全部成功。Windows 专项运行、旧 amd64 单架构 CI 及旧提交的成功结果不能用于发布。
4. 给通过完整 CI 的同一提交打标签并推送：

```bash
tag="v$(cat VERSION)"
git tag -a "$tag" -m "ALinkSec $tag"
git push origin "$tag"
```

5. `Release` 校验版本、`main` 祖先关系、同一提交的完整 CI 和三个未过期 Agent 附件；在 amd64/arm64 原生 runner 上分别串行构建三种镜像。每种架构都通过服务端启动/重启/API/TLS、Web HTTPS/API、SQLite 备份恢复冒烟后，推送架构标签并保留 digest。两组均成功后，按不可变 digest 校验平台/版本/提交并合并镜像索引，核对索引确实包含两种已测试镜像，最后生成附件及 GitHub Release。
6. 核对 Release 成功、六个附件齐全，执行 `sha256sum --check SHA256SUMS`，按 [部署文档](06-部署文档.md)拉取镜像并安装与主机架构匹配的 Agent。

Windows Agent 附件来自实际 SCM 服务测试使用的 exe；两个 Linux 附件分别来自对应原生架构上 Agent 联动测试使用的二进制。三者复用同一次完整 CI 成品，并在打包时检查 ELF/PE 的实际架构。发布作业重新构建同一提交的容器并原生冒烟。

## 重试与失败

仅在完整 CI 成功后推送发布标签；标签不可重新指向另一提交。CI 成品保留 14 天，过期需在标签对应的 `main` 提交重新执行完整 CI。发布前的失败不会创建 GitHub Release；推送途中失败可能已有部分同版本镜像，需要重跑同一标签完成剩余步骤。

可从 Actions 界面重跑失败作业，或执行 `gh workflow run Release -f tag="v$(cat VERSION)"`。GitHub Release 已创建后不重复运行发布；任何内容修正使用新版本。`Release` 同标签串行执行，不取消正在运行的发布。

当前开发阶段的发布验收依据见 [封版缺陷清单](07-封版缺陷清单.md)、[全功能联动](10-本机全功能联动验收记录.md)和 [原生 Agent 验收](12-原生Agent本机验收记录.md)。

## v0.0.1 本机最终检查

2026-10-02 串行完成 Maven 60 项测试与 `0.0.1` 打包、Go 全套测试和 Linux 成品构建、前端 6 项测试、部署 9 项及发布门禁 3 项检查。Linux 成品 `version` 输出为 `alinksec-agent 0.0.1`。版本/默认镜像一致性、两份工作流 actionlint、文档本地链接及 diff 格式检查通过。

Maven/Go 构建前暂时停止本机后端，采用 256 MiB 构建堆、单 worker 和 384 MiB 最低可用内存监控；未触发资源停止阈值。构建结束恢复原有 server，HTTPS 健康检查正常，运行中容器仍只有原有 server/web。发布以同一提交的完整 CI 和 Release 实际结果为准，run ID 与镜像 digest 自动写入产物 manifest。
