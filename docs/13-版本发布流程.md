# ALinkSec 版本发布流程

适用版本：v0.0.1。发布目标为 GitHub `wybroot/alinksec` 和 Docker Hub `wangyanbiao/alinksec`。

默认入口为英文 [README](../README.md)，中文入口为 [README-cn](../README-cn.md)，两版互相切换；发布包携带两版完整文档。

## 产物

| 产物 | 地址或名称 |
| --- | --- |
| 服务端，Linux amd64 | `wangyanbiao/alinksec:server-v0.0.1` |
| Web，Linux amd64 | `wangyanbiao/alinksec:web-v0.0.1` |
| SQLite 维护工具，Linux amd64 | `wangyanbiao/alinksec:sqlite-maintenance-v0.0.1` |
| 源码、部署文件和全部文档 | `alinksec-v0.0.1.tar.gz` |
| Linux 原生 Agent | `alinksec-agent-linux-amd64` |
| Windows 原生 Agent | `alinksec-agent-windows-amd64.exe` |
| 产物 SHA256 | `SHA256SUMS` |
| 提交、完整 CI、资产校验与镜像 digest | `release-manifest.json` |

三个组件使用同一个 Docker Hub 仓库的独立标签。v0.0.1 不发布无组件名的 `latest`，也不发布 Agent 容器或 ARM64 产物。正式部署可以用 manifest 中的 `repository@sha256:...` 覆盖 Compose 的 `ALINKSEC_SERVER_IMAGE`、`ALINKSEC_WEB_IMAGE`、`ALINKSEC_SQLITE_MAINTENANCE_IMAGE`，固定实际镜像。

## 仓库配置

在 GitHub Settings → Secrets and variables → Actions 配置：

- `DOCKERHUB_TOKEN`：有 `wangyanbiao/alinksec` 推送权限的 Docker Hub token。
- 也兼容已有 `DOCKERHUB_PASSWORD`，建议其中保存访问 token；若两个名称都存在，优先使用 `DOCKERHUB_TOKEN`。
- `DOCKERHUB_USERNAME`：可选，必须为 `wangyanbiao`，未设置时使用该值。

GitHub Release 使用工作流自身的 `GITHUB_TOKEN`，发布作业声明 `contents: write`；CI 查询和附件下载声明 `actions: read`。不需要把 GitHub 或 Docker Hub 凭据写入源码、Compose、日志或发布包。

## 发布顺序

1. 更新 `VERSION`、六份 Maven POM、Agent 产品版本、前端 `package.json/package-lock.json`、两份 Compose 的默认镜像标签和发布说明。
2. 串行执行本机可安全运行的检查。`node deploy/release/check-version.mjs v0.0.1` 检查版本和默认镜像；`node --test deploy/tests/release-gate.test.mjs` 验证发布门禁。低内存主机遵守仓库 `AGENTS.md`，重构建有内存监控，前端构建前暂停后端。
3. 提交并推送到 `main`，等待该提交的完整 `CI` 通过。三个作业 `windows-agent`、`build-and-test`、`schema` 必须全部成功。Windows 专项运行及旧提交的成功结果不能用于发布。
4. 给通过完整 CI 的同一提交打标签并推送：

```bash
git tag -a v0.0.1 -m "ALinkSec v0.0.1"
git push origin v0.0.1
```

5. `Release` 工作流校验标签对应版本、`main` 提交祖先关系、同一提交的完整 CI 和未过期的 Agent 附件，再串行构建三种镜像。实际发布镜像的服务端启动/重启/API/TLS、Web HTTPS/API、SQLite 备份恢复冒烟通过后，依次推送 Docker Hub，生成校验和及 digest 清单，最后创建 GitHub Release。
6. 核对 Release 成功、五个附件齐全，执行 `sha256sum --check SHA256SUMS`，按 [部署文档](06-部署文档.md)拉取镜像并原生安装 Agent。

Windows Agent 附件来自实际 SCM 服务测试使用的 exe；Linux 附件来自实际 Agent 联动测试使用的二进制。两者均复用完整 CI 的成品。发布作业重新构建同一提交的容器并冒烟，避免仅发布未经启动验证的镜像。

## 重试与失败

仅在完整 CI 成功后推送发布标签；标签不可重新指向另一提交。CI 成品保留 14 天，过期需在标签对应的 `main` 提交重新执行完整 CI。发布前的失败不会创建 GitHub Release；推送途中失败可能已有部分同版本镜像，需要重跑同一标签完成剩余步骤。

可从 Actions 界面重跑失败作业，或执行 `gh workflow run Release -f tag=v0.0.1`。GitHub Release 已创建后不重复运行发布；任何内容修正使用新版本。`Release` 同标签串行执行，不取消正在运行的发布。

当前开发阶段的发布验收依据见 [封版缺陷清单](07-封版缺陷清单.md)、[全功能联动](10-本机全功能联动验收记录.md)和 [原生 Agent 验收](12-原生Agent本机验收记录.md)。

## v0.0.1 本机最终检查

2026-10-02 串行完成 Maven 60 项测试与 `0.0.1` 打包、Go 全套测试和 Linux 成品构建、前端 6 项测试、部署 9 项及发布门禁 3 项检查。Linux 成品 `version` 输出为 `alinksec-agent 0.0.1`。版本/默认镜像一致性、两份工作流 actionlint、文档本地链接及 diff 格式检查通过。

Maven/Go 构建前暂时停止本机后端，采用 256 MiB 构建堆、单 worker 和 384 MiB 最低可用内存监控；未触发资源停止阈值。构建结束恢复原有 server，HTTPS 健康检查正常，运行中容器仍只有原有 server/web。发布以同一提交的完整 CI 和 Release 实际结果为准，run ID 与镜像 digest 自动写入产物 manifest。
