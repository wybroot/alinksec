# 证据回执并发读取与失败诊断

> 版本基线：v0.0.4。本文区分源码／CI 证据和现场待验收；真实系统、持续稳定性、规模和私有服务不因版本发布而改为通过。版本差异见[发布说明](releases/v0.0.4.md)，全部资料见[文档索引](README.md)。

原生集中取证验收在真实 Agent 重启后，要求待发送文件逐字节重放；收到经过 mTLS 的精确回执后，要求持久化对应命令的完成记录并移除待发送项。原有七项检查全部保留。

## 并发读取

原验收每 20 毫秒使用 `os.ReadFile` 读取 `evidence-state/pending.json`。这个 Windows 读取方式未启用 `FILE_SHARE_DELETE`，持有句柄期间可能阻碍 Agent 原子替换记录。验收改用已有 `securestate.ReadJSONLimit`，通过允许删除共享的句柄读取完整快照，继续执行 4 MiB 上限和严格 JSON 校验。仍每 20 毫秒观察，等待上限仍为 10 秒；现在还核对完成记录的命令 ID、命令摘要、有效期和成功状态。

Windows 定向回归直接调用生产回执事务，并持有实际文件句柄：普通读者作为冲突对照，检查写入失败后原文件和完成状态未改变，原文件仍可完整重放，关闭读者后同一回执可恢复提交；允许删除共享的读者则检查提交成功，旧句柄仍读取旧快照，新读取看到精确完成记录，私有 DACL 保留。

有关 Windows 共享模式和原子替换的接口约束，参见 [Microsoft CreateFile 文档](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) 与 [FILE_RENAME_INFORMATION 文档](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information)。

## 重复执行与诊断

Linux amd64、Linux arm64、Windows Server 2022 和 2025 的原生取证脚本均执行三次独立进程，每次重新注册并建立私有工作目录。任一次失败立即停止，不把后续重复当作失败重试。每次都保留原七项验收、诊断包摘要、两次回执观察和测试日志；保留最终一次的 `result.json` 与 `diagnostic.zip` 供原有验收读取。`attempts.json` 记录三次原件摘要。

`observations.json` 记录固定回执上限、命令 ID、是否已提交、观察耗时、读取次数和错误信息。失败时额外保留最后 64 KiB 的隔离测试进程日志，遮蔽固定测试注册令牌。CI 在失败后仍上传这些文件。不会复制配置、私钥或原始状态文件。生产日志补充回执及日志读取失败的底层错误，以便区分文件共享冲突、权限、格式和存储异常。

## 验收边界

main CI 40153803776 的 Windows 2022 首次执行曾在 10 秒内未观察到回执持久化，原代码单次复验通过。首次进程日志未被原流程保留，因此该次失败的根因尚未证明。上述对照可验证普通读者造成的故障机制，不能追认它就是那次历史失败的唯一原因。原失败日志和所有官方产物仍保留在 `/root/work/validation-records/final-hardening`。真实现场系统、私有服务、实际补丁重启、200 台主机 72 小时和 1 秒指标目标继续独立验收。
