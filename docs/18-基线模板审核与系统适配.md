# 基线模板审核与系统适配

平台覆盖 Agent 支持的 Linux、Windows 两种系统类型。核查默认根据 Agent 上报的 `os_type` 和 `os_version`，为每台主机选择已发布且适用的模板；同一任务可以包含不同系统的主机。可以按产品、发行版和版本逐步扩充模板，无需为新模板替换检查引擎。管理员仍可指定模板集合。

全系统适配流程不等于所有系统已有完整合规内容。旧内置 Linux 模板在 V006 中停用并保留历史；本轮提供 Linux、Windows 各四项的基础核查候选包，供启动审核流程，不宣称符合完整等保、CIS 或 STIG 基线。未支持规则单独列出原因，不进入可执行项或通过率的分母；得分仅表示已执行检查的结果。未被模板覆盖的主机明确列出，并阻止整次任务下发。

## 1. 准备候选包

构建两种平台的基础候选包：

```bash
python3 -B deploy/baseline/build-package.py --output-dir .tmp/baseline-candidates
```

也可以直接使用 [Linux 候选包](../deploy/baseline/packages/linux-baseline.json) 和 [Windows 候选包](../deploy/baseline/packages/windows-baseline.json)。版本 2 Linux 包只观察广播回显忽略、SYN Cookie、all 重定向和 all 源路由参数；Windows 包查询三个实际存在的防火墙配置的有效策略、Defender 实时保护、事件日志服务和 UAC。候选具有明确产品和版本匹配范围；具体组件与版本仍须测试。候选包使用本轮 Agent 中编译的固定命令集，不包含修复脚本。Windows 检查需要同步更新本轮 Agent；旧 Agent 会拒绝新命令，不能把拒绝结果解释为符合基线。

旧 60 项的逐项审核、8 项参考观测候选与 52 项未支持原因见 [内容审核记录](20-旧基线模板内容审核.md)。

文件格式为 JSON，最多 2 MiB、500 项可执行检查、2000 项原始规则。内容包含：

| 字段 | 用途 |
|---|---|
| `schemaVersion` | 当前为 `1` |
| `code`、`version` | 模板系列与不可变版本；同版本不同内容拒绝导入 |
| `name`、`standard`、`product` | 名称、标准与产品范围 |
| `osType` | `1` Linux、`2` Windows |
| `osVersionPattern` | RE2 完整匹配 Agent 上报的版本文本，必须以 `^` 开始、以 `$` 结束；`^.*$` 为该系统类型全部版本 |
| `source` | 来源名称、版本、HTTPS 链接和原始内容 SHA256 |
| `items` | 规则编号、名称、类别、严重度、声明式 `check` 与人工处置说明 |
| `unsupported` | 不能转换的原始规则编号和原因 |

系统版本文本来自 Agent 实际采集，例如 `ubuntu 24.04`、`rocky 9.4`；不要只依据控制台显示的友好名称编写适用表达式。模板内容另外计算规范 JSON 的 SHA256，空白和字段顺序变化不创建不同内容。来源摘要是审核者提供的出处信息；平台导入时不会访问该 URL、下载来源或验证远端签名。

## 2. 审核、测试和发布

在“基线模板”页面按以下顺序操作：

1. 管理员导入候选包，查看来源、产品范围、原始规则编号及相对当前发布版本的新增、修改、撤销差异。
2. 填写审核说明后通过或拒绝。通过后生成不可选的候选模板；此操作不下发检查。
3. 选择 1 至 10 台适用测试主机，明确点击“下发测试核查”。此步骤只核查，不执行修复。离线主机使用现有指令队列，未完整返回结果前不能发布。
4. 完整核查后检查结果，填写发布说明。所有检查必须返回明确的通过或不合规状态；执行异常或旧 Agent 的无法确认结果会阻止发布，需要处理原因并发起新测试。测试主机本身可能存在不合规配置，因此不要求得分必须为 100；管理员应说明失败项及处置方式。
5. 发布后模板进入可选集合，并替换该系列此前的发布版本。发布不会自动核查其他主机。撤回会停止新任务选择该版本，已经下发的任务继续使用其快照。

测试结果可展开查看每项实测值和失败原因，再决定是否发布。每个版本的文档不可修改。来源、适用范围或检查项变化需使用新版本号重新导入；同系列仅有一个当前发布版本。候选包记录其导入时的发布版本。如果审核期间另一版本已发布，旧候选不能覆盖新版本，需基于新版本重新导入审查。管理员管理导入、审核、测试、发布和撤回；操作员可以发起普通核查；只读用户可查看模板、差异和结果。所有写操作沿用平台审计。

在“基线核查”中，“按 Agent 系统自动选择”为默认选项。每台主机单次最多下发 500 项检查。选择混合主机后，服务端逐台筛选适用的已发布模板和启用检查项；Windows 不接收 Linux 检查。某台主机没有适用检查时，界面列出该主机并提示补齐模板，避免静默跳过导致任务进度失真。

## 3. 支持的检查边界

`file_content`、`file_line`、`file_perm`、`cmd_output` 沿用 [Agent 检查格式](../agent/internal/baseline/spec.go)。文件检查必须指定目标系统的绝对路径；`file_perm` 只支持 Linux。正则使用线性时间的 RE2 语法；不接受 Java 回溯、前瞻和反向引用。命令检查必须精确匹配该系统的 Agent 编译允许列表，导入包无法扩充它。Windows 使用固定的只读 PowerShell 查询；检查超时范围为 100 至 30000 毫秒。

候选包不接受 `fix_spec`、任意脚本或未知字段。执行错误和不合规结果不能视作通过。新增检查类型、原生注册表检查或新的命令选择器需要单独更新 Agent，并与服务端校验同步。允许列表和共同迁移的两端一致性由 CI 检查。

Agent 每项回报 `pass`、`fail` 或 `error`，分别表示通过、不合规和执行异常。缺失文件按不合规返回；权限不足、读取不完整、命令错误、超时及无效定义按执行异常返回。每台主机串行执行，最多 500 项；命令总输出最多 64 KiB，超限立即终止，继承管道等待最多 250 毫秒。Linux 命令超时会终止进程组。内容读取只允许普通文件，最多 8 MiB、16384 行、单行小于 1 MiB；扫描检查截止时间，无法完整读取时不能得出“未包含”的通过结论。文件系统调用仍受底层存储响应约束。任务超过 20 分钟预算后，剩余项回报执行异常。实测值和原因分别限制为 2 KiB 和 1 KiB 的有效 UTF-8 文本，500 项回报可在默认 gRPC 消息上限内传输。

## 4. 上游 XCCDF 的可追溯转换

可以按 [ComplianceAsCode 明确发布版本](https://github.com/ComplianceAsCode/content/releases) 取得对应产品的独立 XCCDF Benchmark。其 [构建说明](https://complianceascode.readthedocs.io/en/latest/manual/developer/02_building_complianceascode.html) 描述输出形式；完整 XCCDF/OVAL 仍需要独立解释器。

`build-package.py` 提供人工审核映射的包构建入口：在自定义定义文件的对应 `platforms.linux` 或 `platforms.windows` 中，填写 `upstreamSha256`、来源版本及每个已审查规则的 `ruleId` 和声明式检查，然后运行：

```bash
python3 -B deploy/baseline/build-package.py \
  --definitions reviewed-mappings.json --platform linux \
  --xccdf ssg-product-xccdf.xml --output-dir .tmp/baseline-candidates
```

工具核对整个 XCCDF 文件的固定 SHA256，并确认映射编号存在、无重复。未映射的规则全部写入 `unsupported`。它不会解释 OVAL、运行上游修复脚本、从自然语言生成 Shell，或把产品中全部规则宣称为某个合规 Profile 的通过率。不同产品和版本应分别准备定义文件与候选版本；上游文件变化后重新审核映射和摘要。

## 5. 历史任务与升级

`V004__baseline_packages.sql` 增加候选记录、系列发布锁、任务模板/检查快照和每台主机实际下发项。新任务保存模板版本、包摘要、规则编号、检查和修复定义；模板快照与待发指令在同一事务中保存，提交后由有界单线程队列发送，避免快速回报早于任务落库，也避免 SQLite 提交回调占用写事务时嵌套发送。队列满或发送失败时，待发指令仍在数据库保留，沿用 Agent 重连补推。查询历史名称、类别、严重度和版本时优先使用快照。接收结果必须覆盖该主机全部实际下发项，无重复或额外项；其他主机不能给任务增加完成数。

`V005__baseline_execution_evidence.sql` 保存执行状态、耗时及异常数量。旧结果保留原有实测值和原因，标记为 `legacy`，不推断其失败是执行异常还是不合规。旧 Agent 可以继续回报普通核查，但不能用于新候选发布或自动修复；Linux 与 Windows 均需升级 Agent 后重新测试。页面分别统计不合规、执行异常和旧结果；含旧结果的主机不显示确定的合规率。

旧任务已有结果在迁移时复制当时可用的定义，无法重建迁移前已经被覆盖的定义；升级前正在执行的旧任务保留原查询兼容路径。新模板版本不会改变新任务已经保存的解释。新任务首次接受的完整回报不会被重传覆盖；重测须创建新任务。并发回报按任务串行提交，避免 PostgreSQL 丢失完成进度；超时后的部分回报保留超时状态，收齐后完成，取消后的回报丢弃。

配置修复接口再次校验最近下发任务的结果，要求明确的不合规状态、当前系统适用、模板与项仍启用，以及历史检查/修复定义与当前内容一致。成功、异常、旧结果、过期定义或已撤回模板均拒绝自动修复；存在更新的待回报核查时也暂停旧证据修复。旧任务晚到不能覆盖较新任务的合规结论，缺少定义快照的结果须重新核查。直接调用 API 遵守相同约束。修复指令也在事务提交后发送。

`V006__retire_legacy_baseline.sql` 停用旧 Linux 参考模板和 60 项旧检查，清除旧自动修复，修正当前中文说明；旧任务快照和结果原样保留。V007 进一步让日志查询跟随符号链接最终目标、核对普通文件类型和数值属主 UID；不会改写 V006。更新两端后导入新候选并重新审核、测试、发布。下发、审核和发布均按当前检查策略校验，旧测试不能恢复已移除的查询。

SQLite 在启动时自动应用迁移；PostgreSQL 先执行现有迁移脚本，再启动应用。脚本会在短暂模板表锁下把自增序列前移到已分配 ID 之后，避免旧初始化中显式插入的内置模板 ID 与审核新模板冲突；重跑不会回退已有序列。应用角色继续仅需 DML 权限，无需修改已发布迁移。备份应包含所有新增表；旧服务端不能识别新模板流程，不应回退后继续修改其数据。

## 6. API

| 接口 | 权限与用途 |
|---|---|
| `GET /api/baseline/packages` | 已登录用户；最近 200 个版本摘要 |
| `GET /api/baseline/packages/{id}` | 已登录用户；来源、差异、测试结果和适用测试主机 |
| `POST /api/baseline/packages/import` | 管理员；multipart 字段 `file` |
| `POST /api/baseline/packages/{id}/review` | 管理员；`{"approved":true,"note":"审核说明"}` |
| `POST /api/baseline/packages/{id}/test` | 管理员；`{"agentIds":["test-host"]}` |
| `POST /api/baseline/packages/{id}/publish` | 管理员；`{"note":"测试结果和发布说明"}` |
| `POST /api/baseline/packages/{id}/withdraw` | 管理员；`{"note":"撤回说明"}` |
| `POST /api/baseline/coverage` | 管理员、操作员；核查前预览，`agentIds` 与可选 `templateIds` |
| `POST /api/baseline/tasks` | 管理员、操作员；省略或传空 `templateIds` 时自动选模 |

验证区分真实原生检查、服务端协议夹具和生产包浏览器回放。浏览器使用实际测试 API 捕获的响应；完整测试结果采用协议夹具，不代表已经接入生产 Linux/Windows 主机或完成完整合规标准认证。Windows 原生命令执行由 Windows CI 验证。

独立 Ubuntu 24.04 OpenSSH 候选使用 `sshd_effective` 检查；配置路径、选项及连接条件都进入审核定义与任务快照。该类型需要更新服务端与 Agent，旧 Agent 返回执行异常并阻止发布。具体范围与样例连接重建方式见 [OpenSSH 配置核查](21-OpenSSH配置核查.md)。

独立 Ubuntu 24.04 本地身份候选使用 `local_identity_file` 和 `local_accounts`。固定文件、权限允许位上限、数值属主/属组及显式 UID 范围进入不可变审核与下发快照；改变范围须新版本重新审核、测试。扩展访问 ACL 或无法确认、读取失败、文件变化、旧 Agent 不支持都保持执行异常，不能发布。账户证据只含名称与数量，不输出口令字段或哈希；参考 shell 集合不能替代账户锁定或 PAM/NSS 生效判断。两端均需升级，边界与生成方法见 [本地身份文件核查](22-本地身份文件核查.md)。

独立 Ubuntu24.04 passwd PAM 候选的两项检查限定服务与已支持本地口令链，明确质量参考、root 例外和口令传递，散列项只核对新口令的显式选择。未知链/配置异常阻止发布，生产检查不更新口令。需更新两端并重审测试，范围与隔离原生验证见 [PAM口令链核查](23-PAM口令链核查.md)。

独立Ubuntu24.04 login PAM候选的 `pam_auth` 项限定已支持auth链，分别核对失败次数、窗口、三个阶段一致配置及普通/root有限解锁参考。未知链或读取异常阻止发布，生产检查不尝试登录、不修改计数，也不提供自动修复。详见 [PAM登录失败锁定核查](24-PAM登录失败锁定核查.md)。

独立 Ubuntu24.04 systemd 候选的 `systemd_service` 项限定本地系统管理器的 auditd/rsyslog 单元，保存加载、运行状态和主进程证据。总线不可达、单元缺失、加载异常或切换状态保持执行异常并阻止发布；当前服务状态不能证明审计事件或日志投递。生产检查只读，不管理服务，见 [systemd服务状态核查](25-systemd服务状态核查.md)。

独立 Ubuntu24.04 固定日志元数据候选限定审计目录与btmp/wtmp路径、模式位上限和数值ID；ACL、链接、路径缺失/变化或无法取证保持error并阻止发布，不证明实际日志目标、内容、轮转或写入。两端需升级且无自动修复，见 [固定日志元数据核查](26-固定日志元数据核查.md)。

独立 Ubuntu24.04 内核审计候选只读内核启用状态与当前加载的有限身份文件watch规则；抑制/未知规则、权限或命名空间不足及变化保持error。管理员确认产品范围后测试，见 [内核审计核查](27-内核审计与身份文件watch核查.md)。

新增 auditd 磁盘配置候选提供本地写入声明、keep_logs声明和配置所指日志目标元数据三项，明确不证明运行实例已加载或交付日志，不替代旧sudo/cron规则；旧60项当前19项尚未实现。边界与原生解析验证见 [auditd磁盘配置与日志目标核查](28-auditd磁盘配置与日志目标核查.md)。

Ubuntu24 sudoers 独立候选将旧0018/0029收窄为有限磁盘认证和获准命令日志声明，不证明实际授权、每次认证或日志交付。定义与任务快照保持完整参考，边界见 [sudoers磁盘策略核查](31-sudoers磁盘策略核查.md)。当前旧60项中41项具有限定范围实现，19项尚未实现。
