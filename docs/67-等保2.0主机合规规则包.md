# 等保 2.0 主机合规规则包

本模块提供 GB/T 22239-2019 二级、三级“安全计算环境”的 Linux / Windows 候选包。二级按 7.1.4 列出 23 个细分条款，三级按 8.1.4 列出 34 个细分条款；每个条款均有自动证据映射或人工取证要求。目录中的摘要和取证说明由项目编写，条款编号用于对应标准。

国家标准信息公共服务平台的[标准信息](https://std.samr.gov.cn/gb/search/gbDetailed?id=88F4E6DA63434198E05397BE0A0ADE2D)标明该标准现行，2025-05-30 复审结论为继续有效。条款编号与数量另以[公开标准文本](https://ic.tcu.edu.cn/611.pdf)核对。本包面向主机安全计算环境；物理、网络、管理制度以及云计算、移动互联、物联网、工业控制扩展要求需要相应范围的独立测评。

## 候选包和适用范围

| 包 | 系统范围 | 自动证据检查 | 条款 |
| --- | --- | ---: | ---: |
| `packages/compliance/level2/linux-baseline.json` | Ubuntu 24.04 LTS | 56 | 23 |
| `packages/compliance/level3/linux-baseline.json` | Ubuntu 24.04 LTS | 56 | 34 |
| `packages/compliance/level2/windows-baseline.json` | Windows 10/11、Server 2019/2022/2025 | 17 | 23 |
| `packages/compliance/level3/windows-baseline.json` | 同上 | 17 | 34 |

路径均相对 `deploy/baseline/`。未知系统版本无法选择这些包。Linux 沿用经过审核的有限检查实现及组件版本约束；发行版名称匹配不保证每个组件可执行。缺少对应组件、权限或无法读取有效配置时，检查保留失败或异常，发布仍要求完整且无执行异常的测试结果。Debian、RHEL、Rocky 不在这组完整包的适用范围内，原有独立候选继续保留其各自范围。

Linux 自动证据覆盖本地身份文件、PAM、Shadow 新账户默认值、Bash、明确连接条件的 OpenSSH、审计、日志元数据、服务、软件源声明、AppArmor 和当前 Agent 等。已有检查的边界继续适用：示例 SSH 连接不能代表全部管理入口，配置声明不能证明实际授权、历史账户或日志交付。需按现场连接条件审核相应定义后生成新的候选版本。需要现场角色/参考清单的 IPv4 检查、特权文件摘要和登录横幅没有作为预设现场事实打包；相关业务边界由条款取证要求覆盖。

Windows 在原有防火墙、Defender、EventLog、UAC 4 项基础上，增加 13 项固定原生安全策略检查：

- 使用 `NetUserModalsGet` 读取本机 SAM 的口令长度、有效期、历史和锁定策略；不获取口令或散列。
- 使用 `AuditQuerySystemPolicy` 按固定 GUID 读取登录、账户管理、审计策略变更、系统完整性的成功/失败审计配置，不依赖本地化命令文本。
- 读取固定注册表路径的 RDP NLA、TLS/加密强度、NTLM 和空闲锁定声明；不把本机声明当作域细粒度策略、应用账户或实际会话的完整证据。
- 使用固定允许列表中的只读 `Get-WindowsOptionalFeature` 查询 SMB1Protocol，明确禁用或移除有效载荷才通过；组件、权限或查询缺失不会按禁用处理。

口令长度 12、有效期 90 天、失败阈值 1 至 5、900 秒锁定/空闲等是项目建议参考，标准没有在上述条款逐一规定这些数值。采用其他阈值需提供新的审核目录和对应检查实现；不能在本包保留同一目录声明的同时削弱检查。Windows 查询仅访问本机，权限不足返回执行异常，不修改安全策略。

## 目录完整性与来源

`deploy/baseline/compliance/catalog.json` 保存两份条款目录、各系统必需的检查映射和人工取证要求；`definitions.json` 保存审核后的检查定义。生成器不下载或执行检查：

```sh
python3 deploy/baseline/build-compliance-pack.py
python3 deploy/baseline/build-compliance-pack.py --check
```

生成物包括四个候选包和服务端编译资源 `baseline/compliance-catalog.json`。`source.sha256` 是目录原始字节、NUL 分隔符和定义原始字节的 SHA256；它标识项目审核输入，不宣称是国家标准文件的摘要。每个包另绑定所选目录规范化 JSON 的 `catalogSha256`。

格式版本 2 在原有候选包边界上增加 `compliance`：`catalogId`、`catalogSha256` 和 `controlChecks`。服务端使用编译目录校验，拒绝未知目录、摘要不一致、缺少条款、缺少必需自动证据、未知/重复检查引用、没有映射的检查及削弱必需证据含义的检查改写。允许调整经过基础格式校验的执行超时和明确的 SSH 连接条件，变更会进入包及任务快照。格式 1 继续支持原有独立模板；完整包保留编号前缀不能被降级为格式 1。导入仍不执行检查，也不获取来源链接。

目录 ID 和条款语义一经发布应保持不可变；更新取证要求或必需检查时应保留旧目录并新增 ID。任务通过候选包内容摘要、目录摘要、模板版本及逐项定义快照绑定历史，评估时重新核对包和任务快照，检测到不一致即拒绝产生结论。

## 使用和条款复核

1. 按项目保护等级和主机系统选包，在“基线模板”导入、审核、向适用测试主机下发核查并发布。全部自动证据收齐且无异常是发布条件，实际未通过项需在发布说明中评估。人工条款尚未复核不会被改为自动通过。
2. 发起基线核查。若同时发布二级和三级模板，现有自动选模会选择两者；只核查一个等级时应显式选择模板或仅发布所需等级。
3. 在主机核查明细打开“等保条款与证据”。查看所有 23 / 34 条及各条款自动证据、尚需的业务/现场材料。自动检查得分与条款结论分别展示。
4. 管理员填写至少 10 字依据及受控证据索引，选择通过、未通过、不适用或重新取证。证据索引可写工单、材料路径及 SHA256；平台按文字保存，不主动访问该索引。不适用需说明适用性依据。
5. 导出 JSON，保存包摘要、检查实测值、人工依据、证据索引、账号、时间及复核版本。平台保存的是证据索引，受控材料本身仍须按组织的证据管理制度保存。

所有条款初始待核验。含自动证据的条款即使全部检查通过，仍须结合人工材料确认；备份恢复、个人信息处理、输入有效性和可信链等需要相应业务测试或现场材料。自动证据缺失、旧结果、异常或未通过时，不能人工确认通过或不适用。需先整改并发起新的核查，保留原任务历史。

复核记录采用追加版本，同一任务锁与结果入库串行，客户端提交上一版本号，过期提交拒绝。重新取证追加待核验记录，保留此前决定。撤回候选模板不改变历史任务；失败刷新清除页面旧条款统计。admin 可以复核，operator / viewer 可以读取和导出，写操作进入现有审计日志。

API：`GET /api/baseline/tasks/{id}/agents/{agentId}/compliance`；管理员使用对应 `/compliance/review` 的 POST，提交 `templateId/controlId/revision/decision/note/evidenceRef`。结果中的 `complete` 仅表示没有待核验或执行异常条款，未通过数须同时检查，不能据此声称通过测评。

## 验证

后端集成测试使用真实 SQLite 迁移和事务，验证四份包的完整目录、缺项/降级拒绝、快照不一致、权限、追加历史和自动失败保护。可处置 API 冒烟在 SQLite 和 PostgreSQL 分别验证导入、审核、异常阻断发布、完整报告、并发复核冲突、重新取证及撤回后的历史读取；其中 Agent 回报是明确标记的协议夹具。

Linux amd64/arm64 和 Windows amd64 CI 分别原生执行整份包的 56 / 17 项检查，保留每项 pass/fail/error 原始观测；CI 主机的未通过不代表运行失败，也不宣称该主机符合标准。Windows SAM 查询必须真实返回观测。生产前端浏览器检查使用 API 捕获响应，覆盖四份目录、人工复核、异常限制、证据导出、读取失败重试、角色和手机布局。

V026 为 SQLite / PostgreSQL 增加追加式条款复核记录，旧模板及核查结果继续可读。完整 XCCDF / OVAL 解释属于后续模块，本模块没有引入任意脚本执行。
