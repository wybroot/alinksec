# 漏洞规则来源与回移声明

本阶段在[规则与结果身份范围](47-漏洞规则与检测结果身份范围.md)上保存导入来源、声明与匹配时快照。仍属于同一漏洞模块；厂商引用和引用摘要是导入声明，不会自动变成厂商真实性或补丁适用性已验证的结论。

## 导入与依据

手动入口为鉴权后的 `POST /api/libraries/cves/import`。实际来源固定为 `manual`，导入者来自验证后的 JWT 用户属性。配置情报入口记录配置中的来源 ID；文档自称 `source_id`、`upstream` 等不改变实际来源。平台生成 `provenance`，包含来源、导入方式、规范化入库 JSON 的 SHA256、记录时间、导入者和 `verification=imported_declaration`。根节点不允许提供 `provenance`，规则依据也不能自行添加 `verified` 等真实性字段。

来源选择仍按整个 CVE 执行：人工来源优先，其他来源按配置 ID 排序。它不是厂商可信度排序，也不会自动合并不同来源的声明。其他来源的原记录仍保留；来源撤销、可信度治理和新厂商适配器属于后续来源治理工作。

发行版包规则除了明确的包名、来源、版本方案、发行版版本和架构，还需声明 `evidence`：

```json
{
  "cve_id": "CVE-2099-12345",
  "severity": 3,
  "affected": [{
    "name": "fixture-package",
    "match": "exact",
    "source": "dpkg",
    "version_scheme": "dpkg",
    "distro_id": "ubuntu",
    "distro_version": "24.04",
    "architecture": "amd64",
    "vrange": ">=1.0-1ubuntu2",
    "evidence": {
      "basis": "vendor_advisory",
      "assessment": "not_affected",
      "package_scope": "binary",
      "publisher": "Fixture distributor",
      "advisory_id": "FIXTURE-BACKPORT-1",
      "url": "https://fixture.invalid/advisories/backport-1",
      "notes": "测试声明：上游基础版本仍为 1.0，该发行版修订包含回移。不是实际厂商公告。"
    }
  }]
}
```

`basis` 支持厂商公告引用 `vendor_advisory`、人工分析声明 `manual_analysis` 和上游范围 `upstream`；`assessment` 支持 `affected`、`not_affected`、`unknown`；`package_scope` 支持 `binary`、`source`、`upstream`。说明必填且最多 1024 字符；非人工分析还需发布者、公告编号和引用地址。引用地址必须为 HTTPS，不能包含凭据、查询参数或片段，最长 2048 字符；可选 `sha256` 为小写 64 位摘要声明。平台不请求这些引用地址，也不把声明的摘要当作签名验证。

源码包声明不能直接匹配二进制库存。上游范围不能推断 RPM/DPKG 回移状态；NVD 适配器明确标记上游范围。缺依据、范围不完整或未确定的发行版声明只保留元数据。有效的不受影响声明按完整原生版本评估，不生成待修复项，也不能同时提供自动修复目标。同一安装同时命中受影响和不受影响声明、或不同明确修复目标，会保留冲突及全部命中规则，自动修复被阻止。

## 结果与修复

检测结果记录 `rule_source_id`、`rule_digest`、`rule_evidence` 和 `evidence_status`。规则指纹覆盖来源、CVE 和完整 `affected` 内容；证据快照包含入库记录和命中的规则。记录时间表示平台导入时间，引用网页原文和历史完整文档不在本阶段归档。重新导入或当前规则改变不会用新依据回填保留的结果；未处置且无任务引用的结果仍按重扫机制重建。忽略和待修复引用也区分规则指纹，新声明不会复用旧依据下的处置决定。

列表按安装身份、来源、指纹和声明状态聚合。`identity_current` 与 `rule_current` 分别表示当前库存和当前有效规则是否仍对应。未知、冲突、规则变化或同名多安装的结果不进入自动修复集合；服务端创建与派发均重新核对，保存的修复目标、库存和规则指纹任一变化都会拒绝派发。CVSS 使用检测结果记录值。`fixed_version` 仍是导入者声明，不代表已确认厂商修复版本。

新增 `GET /api/libraries/cves` 支持 CVE/标题查询、分页和最多 100 条每页，返回当前有效来源、规则、入库记录和声明用途。规则库页面按用户点击加载；显示历史来源缺失、源码包或上游限制、公告引用、回移说明和声明摘要。漏洞详情与修复对话框显示匹配时依据，不解析说明中的 HTML，历史不安全链接不会生成可点击地址。手机对话框保留可视宽度。

## 迁移与验证

V010 新增来源和证据列，历史记录默认为未知，不推断来源、不补造旧声明；旧来源的派生可比对标记归零，重新导入后按实际条件重算。PostgreSQL 软件资产版本及检测结果的已装和目标版本列从 64 扩到 255，SQLite 不限制 VARCHAR 宽度且不支持相同的类型修改语句，因此两份迁移保留明确的数据库差异。入库 JSON 与规则指纹递归排序对象字段，数组保留声明顺序，避免 PostgreSQL JSONB 重排字段造成指纹失配。历史 V001–V009 不修改，表数仍为 50。

验证入口包括真实 SQLite 事务与 HTTP 情报的导入原子性、实际来源/用户/摘要、失败保持、二进制/源码/上游限制、完整版本回移声明、冲突、不可变快照、规则变化后的创建和审批拒绝，以及 SQLite/PostgreSQL 实际协议中的长版本存储。真实 Agent 工作流改为鉴权导入后由服务端生成来源快照再审批安装；生产 Nginx/SQLite 浏览器同样通过真实导入与匹配生成新结果，旧结果不回填。独立生产 bundle 浏览器检查引用、元数据用途、冲突、历史不安全内容与手机宽度；合成 API 与真实 API/数据库场景分别记录。

Agent执行能力及安装前后的身份复核见[执行契约](49-软件包修复执行契约与身份复核.md)。整个漏洞模块仍未完成；后续按[模块完善计划](19-模块完善计划.md)完成确认修复版本、真实补丁系统适用性、历史规则迁移、审批权限及并发派发。当前声明检查不能替代这些验证。

当前来源撤销与退役边界见[来源治理](52-安全来源治理与有界NVD同步.md)：已退役来源退出选择，优先公告撤销保留优先位置但不参与比对，原始声明与历史证据保留。

厂商原生公告接入现见 [模块 16](70-厂商漏洞公告原生接入.md)：原生解析保留传输来源和原件 SHA-256，不把 TLS 或摘要当作厂商签名验证。仅有修复版本不生成更早版本受影响范围，源码包与 KB 仍保留为元数据。
