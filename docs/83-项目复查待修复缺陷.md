## REV-001：指标文本拼接允许跨主机指标注入

**触发与影响：** 在启用指标转发的部署中，持有合法身份的 Agent 可提交包含换行或指标语法片段的指标名／标签名。外层报告身份虽然通过 mTLS 校验，输出文本仍可插入带另一主机 `agent_id` 的指标行，污染其他主机的监控数据。此问题需要合法 Agent 身份，不是匿名 HTTP 接口绕过。

**代码依据：** [MetricsForwarder.java](../server/alinksec-service/src/main/java/com/alinksec/service/metrics/MetricsForwarder.java) 的 `formatLine()` 直接拼接 `s.getName()` 和标签键，仅转义标签值；[ReportDispatcher.java](../server/alinksec-service/src/main/java/com/alinksec/service/report/ReportDispatcher.java) 将指标报告交给该出口；[MetricSample 协议](../proto/agent.proto) 将名称和标签键定义为字符串。

**复现线索：** 将指标名设置为以下内容，其中两行之间为真实换行：

```text
alinksec_cpu_usage{agent_id="victim",hostname="victim"} 0 1790000000123
alinksec_cpu_usage
```

以 `attacker` 身份格式化后，第一行已独立指定 `victim`，第二行才追加服务端提供的 `attacker` 标签。本轮仅验证字符串输出，真实指标服务接收与查询仍待补充。

**修复方向：** 校验或白名单限定指标名和标签名，拒绝控制字符及非法语法；保留 `agent_id`、`hostname` 等服务端标签，拒绝客户端覆盖或重复声明。

**关闭验收：**

- [ ] 合法指标和特殊字符标签值仍能正常写入、查询。
- [ ] 名称／标签键中的换行、引号、花括号及保留标签重复声明被拒绝。
- [ ] 使用两个隔离测试 Agent，确认 A 的恶意指标不会写入 B 的时间序列；保留真实指标出口验证记录。

## REV-002：报告发送成功但服务端处理失败时可能丢失

**触发与影响：** 普通业务报告发送成功后，服务端发生临时数据库故障或处理异常。Agent 将传输发送成功视为可以出队，服务端则只记录异常，没有通用的持久化成功回执。一次性基线结果或普通安全事件可能丢失。非集群同步路径中的部分报告还会先提交去重记录，再执行业务事务；业务回滚后，同一报告在去重窗口内重试会直接被跳过。

**代码依据：**

- [comm.go](../agent/internal/comm/comm.go) 的 `sendReport()` 调用 `stream.Send()`；`drainQueue()` 在返回成功后调用 `TryAck()` 推进本地队列。
- [AgentChannelImpl.java](../server/alinksec-gateway/src/main/java/com/alinksec/gateway/rpc/AgentChannelImpl.java) 的通用异常分支只记录日志，不返回业务失败回执。
- [ReportDispatcher.java](../server/alinksec-service/src/main/java/com/alinksec/service/report/ReportDispatcher.java) 的 `dispatch()` 仅对部分报告类型包裹外层事务；`dispatchAccepted()` 在分发业务前调用 `tryAcquire()`。
- [BaselineResultService.java](../server/alinksec-service/src/main/java/com/alinksec/service/baseline/BaselineResultService.java) 的结果落库事务不能回滚此前独立提交的去重记录。

**复现线索：** 本轮在内存 SQLite 中执行源码中的去重插入 SQL，首次插入行数为 `1`；模拟后续业务事务回滚，再执行相同插入，行数为 `0`。后续应在非集群部署中注入一次基线落库失败，核查 Agent 出队、服务端去重和任务状态。

**范围说明：** 集群异步收件箱、取证及 Windows 登录等专用回执机制需分别核查，不能将此结论泛化为所有报告都没有持久化保障。指标本身的尽力投递策略也不等同于业务结果可靠投递。

**修复方向：** 业务写入和去重提交保持原子性；普通可靠业务报告在收到持久化成功确认前保留可重放记录。仅在服务端拆流不能保证找回已被 Agent 出队的数据。

**关闭验收：**

- [ ] SQLite 与 PostgreSQL 下，注入一次业务写入失败后，报告能重试成功且不会被残留去重记录阻止。
- [ ] 覆盖发送成功后、业务提交前服务端退出，以及提交后回执丢失，最终业务事实不丢失、不重复生效。
- [ ] 覆盖 Agent 重启和断线补传，确认报告保留期限、容量淘汰及终态任务行为有明确记录。

## REV-003：离线补传的旧资产快照可能覆盖新资产

**触发与影响：** Agent 存在离线积压，重连期间又生成新资产快照。新报告可优先发送，旧队列随后补传；服务端按到达顺序替换资产，没有判断采集新旧。软件版本、端口、进程等可能回退成历史状态，软件快照还会触发漏洞重新比对，错误状态可能持续到下一次有效采集。

**代码依据：** [comm.go](../agent/internal/comm/comm.go) 的发送循环优先处理 `pendingReports`，空闲分支才排空离线队列；[ReportDispatcher.java](../server/alinksec-service/src/main/java/com/alinksec/service/report/ReportDispatcher.java) 传给资产服务的是 `RptAssetSnapshot`，未传外层报告时间；[AssetService.java](../server/alinksec-service/src/main/java/com/alinksec/service/asset/AssetService.java) 的 `replaceSnapshot()` 按类别先删后插，未校验采集顺序。

**复现线索（待执行）：** 保留一份旧软件快照 A，安装或升级软件后生成快照 B；先发送 B，再补传 A，观察资产表与漏洞状态。集群的入站序号表达接收顺序，修复时还需确认其不能把“晚到的旧采集”当作更新的资产。

**修复方向：** 建立可比较且能处理重启的采集版本／顺序，按资产类别防止旧快照覆盖新快照；不要只依靠可回拨的主机墙上时间，也不要仅调整发送优先级。

**关闭验收：**

- [ ] 依次接收 B、A 后，当前资产及漏洞判断仍保持 B。
- [ ] 不同类别的定向采集独立推进，不因另一类别的新报告误丢有效数据。
- [ ] 覆盖普通部署、集群接收、Agent 重启、重复报告及时间回拨场景。

## REV-004：旧 JWT 权限不能统一撤销

**触发与影响：** 用户登出后旧 JWT 仍可重放；即使数据库中账号被禁用或角色被降级，统一拦截器仍按令牌中的旧角色授权。未另行核查当前账号的接口继续可用，最长持续到令牌原有的 12 小时有效期结束。部分业务服务有额外账号校验，此处不表示全部接口均可绕过。

**代码依据：** [AuthController.java](../server/alinksec-gateway/src/main/java/com/alinksec/gateway/rest/AuthController.java) 的登出仅记录审计；[JwtAuthInterceptor.java](../server/alinksec-gateway/src/main/java/com/alinksec/gateway/rest/JwtAuthInterceptor.java) 验证签名、读取令牌角色后授权，没有统一核对当前用户状态或会话版本；[ProtectController.java](../server/alinksec-gateway/src/main/java/com/alinksec/gateway/rest/ProtectController.java) 的规则更新入口及 [ProtectRuleService.java](../server/alinksec-service/src/main/java/com/alinksec/service/protect/ProtectRuleService.java) 未额外核对操作者状态。

**复现线索（待执行）：** 在隔离环境保留一个管理员令牌，分别执行登出、通过测试夹具禁用账号、降级为 viewer，再用旧令牌请求规则更新接口。账号管理界面尚未实现，不能把手工修改测试数据库误写成已存在的产品操作。

**修复方向：** 增加可撤销会话或令牌版本机制，在统一鉴权入口校验账号状态和有效权限；登出、改密、禁用、降权及集群副本间失效语义需一致。

**关闭验收：**

- [ ] 登出后的旧令牌不可继续访问；禁用账号的令牌失效；降权后不能保留旧写权限。
- [ ] 规则修改等没有业务层账号校验的接口也受统一保护。
- [ ] 验证进程重启及多副本请求下的失效一致性；改密功能完成后补充其会话失效用例。

**复现线索（待执行）：** 以管理员登录，对照部署文档寻找改密与用户管理入口；已有账号的隔离数据库中改变初始化密码环境变量后重启，确认旧账号密码不会被更新。本轮已完成前后端源码与文档核对，未进行浏览器或重启实测。

**关闭验收：**

## REV-006：告警中心只读取前 100 条

**触发与影响：** 告警超过 100 条后，后续记录无法通过页面访问。“严重”“高危”“待处置”仅过滤已取回的第一页，可能显示为空，掩盖更早的未处理风险。

**代码依据：** [api/index.js](../web/src/api/index.js) 的 `fetchAlerts()` 固定请求 `/api/alerts?page=1&size=100` 并丢弃总数；[Alerts.vue](../web/src/views/Alerts.vue) 使用本地 `filtered` 筛选，没有分页控件；[AlertQueryService.java](../server/alinksec-service/src/main/java/com/alinksec/service/query/AlertQueryService.java) 后端已支持条件筛选与分页。

**本轮复现：** 使用实际 `fetchAlerts()`，模拟服务端共 101 条告警，前 100 条已处理，第 101 条待处理。函数只发出一次第一页请求，返回 100 条，页面同等筛选得到待处置 `0` 条，而服务端待处置为 `1` 条。

**修复方向：** 将筛选条件交给服务端，保留总数并实现分页；筛选变更时重置页码，避免通过无界拉取全部告警解决遗漏。

**关闭验收：**

- [ ] 超过 100 条时能够翻页访问全部结果；第 101 条的待处置／严重告警可通过对应筛选找到。
- [ ] 总数、页码和筛选一致，处置后刷新不会错误保留或跳过记录。
- [ ] 空数据、请求失败及快速切换筛选时显示正确，旧请求不会覆盖新筛选结果。

## REV-007：标记已处理却提示动作已下发

**触发与影响：** 在告警页面点击“处置”，界面将记录标记为已处置并提示“处置动作已下发”。后端仅更新告警状态，没有创建或发送查杀、隔离等指令，操作人员可能误以为威胁已经被实际处理。

**代码依据：** [Alerts.vue](../web/src/views/Alerts.vue) 的 `handle()` 显示下发成功提示；[AlertsController.java](../server/alinksec-gateway/src/main/java/com/alinksec/gateway/rest/AlertsController.java) 调用查询服务；[AlertQueryService.java](../server/alinksec-service/src/main/java/com/alinksec/service/query/AlertQueryService.java) 的 `handle()` 只执行 `UPDATE t_alert`。

**复现线索（待执行）：** 在隔离环境点击“处置”，记录页面提示、请求响应、告警状态及指令表变化，验证并未产生 Agent 处置指令。本轮仅核查完整调用链。

**修复方向：** 若操作只是人工确认，将按钮和提示明确改为“标记已处理”；若增加实际处置，则需明确动作、目标、权限及 ACK 状态，不能自动把标记操作升级为破坏性响应。

**关闭验收：**

- [ ] 页面用词与实际接口行为一致，人工标记不会宣称已下发或执行安全动作。
- [ ] 若支持实际处置，能够查看指令及成功／失败回执，并区分已下发与已执行。
- [ ] viewer 权限、重复处置和失败提示正确。

## REV-008：负数分页参数绕过 SQLite 数量上限

**触发与影响：** 已认证用户向部分列表接口传入 `size=-1`。控制器只执行 `Math.min(size, 上限)`，负数继续传入 SQL；SQLite 将 `LIMIT -1` 解释为不限制行数，可能返回全部数据并增加数据库、应用内存和响应压力。PostgreSQL 的负数 LIMIT 行为不同，应验证其参数错误处理，不能声称两种数据库都无限返回。

**代码依据：** [AlertsController.java](../server/alinksec-gateway/src/main/java/com/alinksec/gateway/rest/AlertsController.java) 的列表接口及 [AlertQueryService.java](../server/alinksec-service/src/main/java/com/alinksec/service/query/AlertQueryService.java) 直接传递分页值；类似入口存在于 [VulnController.java](../server/alinksec-gateway/src/main/java/com/alinksec/gateway/rest/VulnController.java)、[VirusController.java](../server/alinksec-gateway/src/main/java/com/alinksec/gateway/rest/VirusController.java)、[AuditController.java](../server/alinksec-gateway/src/main/java/com/alinksec/gateway/rest/AuditController.java) 以及 [HostsController.java](../server/alinksec-gateway/src/main/java/com/alinksec/gateway/rest/HostsController.java) 的软件列表。各接口仍有原有角色限制，不是匿名读取绕过。

**本轮复现：** 内存 SQLite 中建立 250 条样本，按控制器逻辑计算 `min(-1, 100)`，执行 `LIMIT ? OFFSET ?`，参数为 `(-1, 0)`，返回全部 250 条。真实接口请求示例为 `/api/alerts?page=1&size=-1`，尚未进行 HTTP 联调。

**修复方向：** 统一校验 `page >= 1`、`1 <= size <= 上限`，非法输入明确拒绝或按统一约定规范化；检查 offset 计算溢出及类似 `limit` 参数，避免只修一个入口。

**关闭验收：**

- [ ] 覆盖负数、零、极大值、整数边界和正常分页，两种数据库均保持有界查询及明确错误响应。
- [ ] 告警、漏洞、病毒、审计、软件清单等同类入口均完成核对。
- [ ] 低权限已认证用户也不能借异常参数触发无界读取；正常分页总数与结果保持正确。

## REV-009：指标缓冲区不能保证容量上限

**触发与影响：** 指标接收持续快于转发，尤其 VictoriaMetrics 连接缓慢、超时或流量突增时，一个 `onBatch()` 可拆分并加入多块数据，最后超限只移除一块。无界队列可以超过注释中的 1000 块上限继续增长，增加服务端内存压力，严重时影响控制面可用性。默认关闭指标的 SQLite 轻量部署不经过该路径。

**代码依据：** [MetricsForwarder.java](../server/alinksec-service/src/main/java/com/alinksec/service/metrics/MetricsForwarder.java) 使用 `ConcurrentLinkedQueue`；`onBatch()` 循环中按约 64 KiB 入队，循环结束后只执行一次 `if (buffer.size() > 1000) buffer.poll()`。`flush()` 每轮最多取 500 块，由单线程同步执行 HTTP 请求，最长等待 5 秒。容量没有按字节强制限制，单个大样本也会先拼接后判断块大小。

**本轮复现：** 用等价的生产者队列计数策略模拟转发线程等待：初始 1000 块，连续 10 批、每批加入 16 块，每批只移除 1 块，最终为 1150 块。该结果证明容量约束失效，不代表已测得某个生产负载会发生 OOM。

**修复方向：** 按记录数和总字节数建立并发安全的硬上限，同时限制单样本及单次发送体大小；明确丢弃策略并暴露丢弃计数，避免转发异常拖垮业务控制面。

**关闭验收：**

- [ ] 在受限资源下持续注入多块批次，并使下游慢响应或超时，队列记录数、字节数及发送体均不越界。
- [ ] 并发上报、超大样本、下游恢复后仍能继续处理，丢弃量有明确观测。
- [ ] 指标过载时登录、心跳、业务报告及指令处理保持已定义的可用性目标。

## REV-010：非集群就绪探针不检查业务依赖

**触发与影响：** 单实例应用仍运行但 PostgreSQL 等业务依赖失效时，`/api/ready` 继续返回成功，不能据此判断是否能处理业务。现有维护工具检查的是 `/api/health`，只能证明代理到应用路由存活；若将其结果用于上线、恢复成功或业务可用性监控，会遗漏数据访问故障。

**代码依据：** [HealthController.java](../server/alinksec-gateway/src/main/java/com/alinksec/gateway/rest/HealthController.java) 的 `ready()` 直接使用 [ClusterRuntime.java](../server/alinksec-service/src/main/java/com/alinksec/service/cluster/ClusterRuntime.java) 的结果，而其 `ready()` 在 `!properties.isEnabled()` 时恒为真；`health()` 本身无依赖检查。[operations.py](../deploy/operations.py) 的 `Deployment.health()` 只核对 `/api/health` 返回 `code=0`。

**范围说明：** 存活探针不检查数据库可以是合理设计；缺口在于单实例没有对应的业务就绪检查，以及恢复后缺少独立业务验证。集群已有依赖检查，不能将本项描述成全部部署的就绪探针都无效。

**复现线索（待执行）：** 在一次性标准单实例部署中启动成功后停止 PostgreSQL，同时请求 `/api/health`、`/api/ready` 及实际数据库查询接口，比较状态。SQLite 另测数据库不可访问或无法完成必要写入的情况。本轮仅核查代码分支，未操作现有数据库。

**修复方向：** 区分进程存活与业务就绪，为单实例补齐有超时和明确故障语义的依赖检查；恢复验证加入必要的数据库与业务事实检查，避免将 HTTP 存活等同于业务恢复完成。

**关闭验收：**

- [ ] 单实例关键依赖故障时就绪返回非成功，恢复后能重新就绪；存活检查仍保持独立语义。
- [ ] 依赖检查有超时及资源上限，不因健康检查制造阻塞或连接耗尽。
- [ ] 维护恢复后验证核心业务及身份材料可用，不只核对 HTTP 存活。

## REV-011：Linux 勒索响应可能误杀无关进程树

**触发与影响：** 诱饵或速率规则触发，响应配置为 `kill`／`kill_and_isolate` 时，Linux 归因可能选择持有同目录其他文件的进程，包括只读进程；找不到该类句柄时，回退到近期启动进程中 PID 最大者。选择条件不能证明该进程修改了受影响文件，却可以进入终止进程及后代的动作链，造成无关业务中断，同时真正写入者可能继续运行。

**代码依据：**

- [attrib_linux.go](../agent/internal/guard/attrib_linux.go) 的 `attributeByOpenFD()` 仅比较文件描述符目标的父目录是否属于受影响目录，未核对目标文件身份、写权限、实际写入或触发窗口；返回遇到的首个匹配进程。
- 同文件 `attribute()` 在句柄归因失败时调用 `attributeByRecency()`；`attributeResponse()` 将候选 PID 交给 `KillProcess()`。
- [respond.go](../agent/internal/guard/respond.go) 的 `attributeByRecency()` 在排除部分路径后，从最近 10 分钟启动的候选中选择 PID 最大者；`respondWithAttributionFiles()` 按配置调用终止函数，`KillProcess()` 递归终止后代及目标。
- [Windows 归因实现](../agent/internal/guard/attrib_windows.go) 已采用实际文件操作证据与进程实例复核，证据不足时跳过终止；此保护不能外推到 Linux 分支。

**复现线索（待执行）：** 在一次性隔离主机中创建受控写入者和只读／无关进程，分别覆盖只读持有同目录其他文件、写入后关闭句柄、多写入者，以及较新无关进程存在的场景。先只调用归因逻辑观察选中对象，再用专用测试进程核查动作。不得在开发机或业务主机上直接运行可能递归杀进程的复现。

**修复方向：** 没有可信写入证据时明确记录未归因并跳过自动终止；需要自动响应时，使用适用系统上的可信文件操作来源与进程实例绑定，终止前再次验证身份和策略。不能仅通过扩大路径排除名单弥补缺失的因果证据。

**关闭验收：**

- [ ] 只读句柄、同目录其他文件、近期启动但无关的进程均不会被终止，也不终止其后代。
- [ ] 写入者退出、PID 复用、多个写入者或证据丢失时，明确未归因并跳过终止。
- [ ] 只有实际写入证据与当前进程实例匹配时才执行获准动作，保留选中依据和最终结果。
- [ ] Linux amd64／arm64 在可丢弃原生环境验证；Windows 原有证据约束保持通过。若修复选择仅告警，文档与界面明确能力边界。

## REV-012：主机离线未生成设计要求的告警

**触发与影响：** Agent 心跳超时后，主机状态变成离线，但不会由该路径形成告警中心记录或通知。运维若依赖告警而不是主动查看主机列表，可能无法及时发现防护失联。

**修复方向与关闭验收：**

## REV-013：采集失败被当作空资产快照

**触发与影响：** 端口枚举或进程枚举接口失败时，Agent 返回空列表但仍声明该类别已采集。服务端删除对应旧资产并写入空集合，使“采集失败”呈现为“没有端口／进程”，丢失此前可用观测。软件采集已有独立状态保护，不能据此认为其他类别也具备相同保障。

**代码依据：** [collector.go](../agent/internal/collector/collector.go) 在调用采集器前写入 `Collected`；`collectPorts()`、`collectProcesses()` 获取列表失败直接返回，没有类别失败状态。[AssetService.java](../server/alinksec-service/src/main/java/com/alinksec/service/asset/AssetService.java) 仅根据 `collected` 对端口／进程表执行先删后插，没有对应成功条件。

**修复方向与关闭验收：**

- [ ] 为各资产类别传递成功、部分、失败、未支持及采集时间，失败保留上次成功数据并标记过期／失败。
- [ ] 先成功采集非空端口／进程，再注入枚举失败，确认数据库和页面不把旧观测变成“当前为空”。
- [ ] 真正成功的空集合仍能清除已不存在资产；单类失败不阻止其他类别更新。核查账户、磁盘和容器同类边界，两种数据库分别验证。

## REV-014：大屏防护效果统计与实际状态不符

**触发与影响：** 大屏的“近 30 日 · 自动处置”使用最近 20 条告警中的非空 `action_taken` 数量，`alert_only` 也被计入，既不是实际自动处置数，也不符合显示的时间范围。引擎列表则把任意主机总防护开关开启当作所有引擎开启，不能反映逐引擎是否可用，可能高估防护效果。

**代码依据：** [api/index.js](../web/src/api/index.js) 的大屏适配中请求 `/api/alerts?page=1&size=20`，以 `filter(a => a.action_taken).length` 生成 `rtHit`；[Screen.vue](../web/src/views/Screen.vue) 将其显示为自动处置数，并给每个引擎统一设置 `on: d.kpi.protectOn > 0` 及相同覆盖比例。已有逐引擎状态接口没有在这段映射中决定对应显示。

**修复方向与关闭验收：**

- [ ] 根据明确时间范围及真实动作终态由后端聚合；仅告警、失败、已下发但未执行不计为成功处置。
- [ ] 超过 20 条记录、跨时间边界及重复事件场景下，展示值仍与独立 SQL 核对一致。
- [ ] 引擎状态使用其自身能力、启用配置、就绪及新鲜度；某个引擎缺失／离线／失败时，不因其他引擎或主机总开关显示正常。
