# 病毒跨卷安全隔离与灾后对账（BKL-016）

> 版本基线：`v0.0.4`（分支 `feat/bkl-016-cross-volume-quarantine-reconcile`，基于合并主线 `main` `a154bbf`）。本文记录 `BKL-016` 在本地完成的源码、跨平台原语、灾后对账、单测与端到端脚本契约更新；真实 Linux 多分区容器闭环、`deploy/tests/detection-workflow.mjs` 实机回放、无沙箱限制的 Windows 原生文件/ACL 测试以及精确提交 27 项 CI 尚未执行，因此 `BKL-016` 维持 `IN_PROGRESS`，不标 `CLOSED`。

## 1. 缺口与目标对照

| 维度 | 原状（`53 号` / `quarantine.go`） | 本次补齐后契约 |
| --- | --- | --- |
| 跨卷 / 跨分区文件隔离 | 仅支持同卷 `renamePinned`，跨卷返回 `EXDEV` / `STATUS_NOT_SAME_DEVICE`，保留原文件并上报处置失败 | 保留同卷优先零拷贝原子路径；触发跨卷错误时自动转入三阶段可恢复跨卷隔离协议（先完整复制到隔离区新 inode 并核对摘要与来源一致性，再安全移除原文件，最后提交 `active` 元数据） |
| 隔离区剩余空间守卫 | 复制/写入前未统一预检可用磁盘空间 | 在写入任何元数据或触碰原文件前，调用 `disk.Usage` 预检隔离区所在卷至少保留 `fileSize + 32 MiB` 可用空间；写入过程遇到 `ENOSPC` / `EDQUOT` / `ERROR_DISK_FULL` / `ERROR_HANDLE_DISK_FULL` / `STATUS_DISK_FULL` 同样安全中止并返回 `insufficient_disk_space` |
| 原路径替换、打开句柄、恢复冲突 | `comm.go` 处置失败一律映射 `file_identity_or_io_failure` | 结构化映射 `ActionErrorCode`：`insufficient_disk_space`、`file_in_use`、`restore_target_occupied`、`parent_directory_changed`、`target_changed`、`quarantine_incomplete`、`quarantine_integrity_failed`、`budget_exhausted`、`file_identity_or_io_failure`；不覆盖新业务文件、不在失败/打开占用时宣称隔离成功 |
| 断电／崩溃后状态对账 | 无启动对账；`deleting` 中断或 `.alinksec-quarantine-*` 暂存残留需本机手工介入 | 启动时 `comm.NewProtected` 自动执行有界 `Reconcile()`（15s 超时，幂等可重复运行），并在 `diagnosticZIP` 的 `runtime.json` 输出纯数值 `quarantineReconcile` 统计（不泄露宿主机路径） |

## 2. 两平台跨卷三阶段隔离协议

所有隔离操作先经过 `openRegular` 与 `openedDigest` 绑定真实目标文件身份与 SHA-256；仅当同卷 `renamePinned` 失败且判定为跨设备错误（Linux `unix.EXDEV` / `syscall.EXDEV`；Windows `windows.STATUS_NOT_SAME_DEVICE` / `windows.ERROR_NOT_SAME_DEVICE` / `syscall.EXDEV`）时进入 `quarantineCrossVolume`：

1. **阶段 A（`prepared`，未触碰原文件）**：
   - 预检隔离区可用空间满足 `fileSize + 32 MiB`。
   - 将已打开且pinned 的源文件句柄 `Seek(0)` 流式受限复制（`maxFileSize = 500 MiB`）到隔离目录临时文件 `<id>.capture-<rand>`。
   - 对目标临时文件重算 SHA-256 核对等于期望摘要，并复核源文件句柄 `SameFile` / `Size` / `ModTime` 未在复制窗口内变化，随后 `Sync()`、关闭、`renameLocal` 发布为 `<id>.payload`（Linux 设为 `0400`），持久化元数据 `transfer_mode = "cross_volume"`。
   - 若阶段 A 任意环节失败（含空间不足、并发写入导致摘要变化、取消超时），仅清理本次 `<id>.capture-*` / `<id>.payload` / `<id>.meta.json`，原文件保持完全未动。
2. **阶段 B（安全移除跨卷源文件，`removeCrossVolumeSource`）**：
   - **Linux**（[fileio_linux.go](../agent/internal/virusscan/fileio_linux.go)）：在原父目录内通过 `unix.Mkdirat` 创建私有 `0700` 暂存子目录 `.alinksec-quarantine-<32hex>` 并先将 `StageDir` 持久化到 `.meta.json`；使用 `unix.Renameat2(..., unix.RENAME_NOREPLACE)` 将原文件移入 `<stage>/victim`，复核 `os.SameFile(origInfo, movedInfo)` 及已打开文件句柄 SHA-256 与期望一致后再执行 `unix.Unlinkat` 删除并清理空暂存目录及 `syncDir(parent)`。若检测到原路径已被新业务文件替换或原文件被并发篡改，则通过 `RENAME_NOREPLACE` 无覆盖移回原路径并干净中止；若回滚也发生碰撞冲突，**绝不删除**未知文件，保留对象并将状态标为 `review_required`。
   - **Windows**（[fileio_windows.go](../agent/internal/virusscan/fileio_windows.go)）：原文件已以 `FILE_SHARE_READ | FILE_SHARE_DELETE`（拒绝 `FILE_SHARE_WRITE`）及 `DELETE` 访问权打开；再次核对父目录中当前路径 `SameFile` 与已打开句柄 SHA-256 一致后，通过 `SetFileInformationByHandle` 调用 `FileDispositionInfoEx`（`FILE_DISPOSITION_DELETE | FILE_DISPOSITION_POSIX_SEMANTICS`，旧系统/文件系统回退 `FileDispositionInfo`）完成已打开句柄删除，并立即关闭句柄触发 NTFS 解除链接。遇到共享/锁冲突或只读映像映射（`STATUS_SHARING_VIOLATION` / `STATUS_FILE_LOCK_CONFLICT` / `STATUS_CANNOT_DELETE` / `ERROR_SHARING_VIOLATION` / `ERROR_LOCK_VIOLATION` / `ERROR_ACCESS_DENIED`）时精确返回 `errFileInUse`（`file_in_use`），同时清理隔离副本，**绝不上报隔离成功**。
3. **阶段 C（提交终态）**：
   - 清空 `stage_dir`，原子更新 `.meta.json` 为 `state = "active"`。

## 3. 删除原子状态与 `RestoreExpected` 句柄收敛

- **删除两阶段持久提交（`DeleteExpectedWithID`）**：校验 `<id>.payload` 摘要通过后，先写入 `state = "deleting"` 并同步，再删除 `<id>.payload`，最后写入 `state = "deleted"`。若删除中途断电且载荷已不存在，重试删除或启动对账均可安全收敛至 `deleted`。
- **恢复前句柄关闭（`RestoreExpected`）**：在 `restoreCopy` 完成并核对写盘成功后立即显式关闭只读载荷句柄再写 `restored` 元数据并删除 `<id>.payload`，避免 Windows 句柄未关闭导致载荷删除滞后或失败。仅 `active` 状态允许 `ExportExpected` 导出取证样本。

## 4. 灾后对账状态机与启动集成

`(q *quarantine) Reconcile(ctx)`（[quarantine.go](../agent/internal/virusscan/quarantine.go)）在孤立隔离锁与私有目录校验下按确定顺序巡检（当 `virus/quarantine` 尚不存在时零副作用直接返回）：

| 发现状态 | 条件与处理策略 | 统计计数 |
| --- | --- | --- |
| `<32hex>.meta.tmp-*` / `<32hex>.capture-*` | 中断写入的孤立临时文件，直接安全删除 | `cleaned_orphan_temp` |
| `restored` / `deleted` 且残留 `.payload` | 元数据已提交终态，清理多余 `.payload` | `cleaned_terminal_body` |
| `deleting` | 删完残余 `.payload` 并提交 `deleted` | `completed_deletes` |
| `active` | 重新校验 `.payload` 存在且 SHA-256 一致（Linux 修复 `0400`）；若缺失或损坏则**绝不删除**，转为 `review_required`（`active_payload_missing_or_corrupt`） | `active_objects` / `review_required` |
| `prepared`（无 `.payload`） | 若存在有效 `StageDir` 且匹配父目录，尝试对 `<stage>/victim` 无覆盖回滚（或清理空暂存目录）；回滚冲突则标 `review_required`，否则清理失效 `.meta.json` 回滚 | `rolled_back_prepared` / `cleaned_stage_dirs` |
| `prepared`（`.payload` 损坏） | 若匹配 `ParentID` 下原文件完好且摘要一致则清理残损临时副本；否则标 `review_required` 留存证据 | `rolled_back_prepared` / `review_required` |
| `prepared`（`.payload` 完好且有 `StageDir`） | 摘要匹配期望则完成 `StageDir/victim` 解除链接并晋升 `active`；摘要不匹配且原名空缺则安全回滚，原名已被占用则标 `review_required` | `promoted_active` / `rolled_back_prepared` / `cleaned_stage_dirs` |
| `prepared`（`.payload` 完好，检查 `OrigPath`） | 原路径已消失或已被替换为摘要不同的**无关新业务文件**时，绝不触碰新文件，安全晋升 `active`；若原文件完好仍在且为 `cross_volume`（阶段 A 崩溃），删除副本回滚清理 | `promoted_active` / `rolled_back_prepared` / `review_required` |
| 损坏 JSON 元数据 / 未知状态 / 无主 `.payload` | **绝不自动删除**，保留现场证据并计入审阅告警 | `corrupt_meta` / `review_required` |

- **启动接入与诊断摘要**：[comm.go](../agent/internal/comm/comm.go) 在 `NewProtected` 中以 15 秒超时执行 `Reconcile`，将异常或待人工复核项记入日志，并将纯数值 `ReconcileReport` 存入 `c.quarantineReconcile`，随 [evidence.go](../agent/internal/comm/evidence.go) 的 `diagnosticZIP`（`runtime.json` 的 `quarantineReconcile` 字段）上报，不含任何宿主机路径。

## 5. `detection-workflow.mjs` 契约联动

[detection-workflow.mjs](../deploy/tests/detection-workflow.mjs#L61-L70) 原先断言容器跨 `/tmp` 与隔离工作目录分区的隔离与删除必须失败。随着 `BKL-016` 落地，已同步更新为验证：
1. 跨卷目标扫描后自动隔离成功（`status === 1`、`action_error === ''`、`quarantine_id` 为 32 位十六进制、原文件已移除）；
2. 原路径存在无关替代文件时，恢复失败且替代文件内容完好；
3. 原路径释放后恢复成功且 SHA-256 精确还原；
4. 恢复后执行删除（无 `quarantine_id` 再次跨卷捕获并销毁）成功且文件移除。
